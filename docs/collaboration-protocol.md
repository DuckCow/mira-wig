# 협업 프로토콜 (ChatGPT × Claude × Codex × 사람)

> **이 문서는 "어떻게 일하나"(규칙·방식)다.** "지금 어디까지 왔나"(상태·결정·다음)는 별도 **핸드오프 문서**가 담는다.
> **사용법**: 새 개발 채팅을 열 때 이 문서 + 최신 핸드오프 문서를 함께 붙인다. Codex는 `AGENTS.md`로 이 규칙 대부분을 자동 적용받는다(겹치는 항목은 AGENTS.md가 코드 측 SSOT).
> **개정 이력**: v2 (2026-07-06) — 결제 코어 재작성 반영: "STRICT 코어 보존(불변)" 규칙을 "변경 규율 + 동결 존"으로 재정의(핵심 엔지니어링 규칙 참조, 코드 측 상세는 `AGENTS.md` §4.5·§8). **v3 (2026-07-06)** — 산출물 저장 규칙 신설(같은 날 salvage notes 복원 사건이 근거 — 상세는 핸드오프 v10 §10). **v4 (2026-08-16)** — 계층형 AI 엔지니어링 거버넌스에 맞춰 단순 build-first 경로와 고위험 경로를 분리하고, 역할·교차검토·MODEL_COMPENSATION 참조를 현행화했다.

---

## 역할

- **사람**: 오케스트레이터. 우선순위·사업 판단·최종 결정. 커밋 실행(수동).
- **ChatGPT**: 설계·검수 에이전트. 전체 궤적·결정 근거·단계 일관성을 보고 제안을 만든다.
- **Claude**: 설계·검수 에이전트. 전체 궤적·결정 근거·단계 일관성을 보고 제안을 만든다.
- **Codex**: 구현·정찰(코드 탐색)·런타임 검증. `AGENTS.md`를 따른다. 실제 시그니처·기존 패턴·무엇이 이미 있는지를 본다.

ChatGPT와 Claude의 설계·검수 결과도 사람 권한 위에 있지 않다. 리뷰와 계획은 입력이며, 사람의 명시적 권한이나 설치된 계약 없이 범위·단계·외부 효과를 확장하지 않는다. 구현 에이전트의 현재 코드 사실과 설계·검수 에이전트의 맥락을 함께 사용하되, 어느 한 에이전트도 사람의 최종 결정을 대체하지 않는다.

---

## 작업 경로

### 단순·가역 경로

```text
필요한 현재 사실 확인 → build → targeted verify → 저장소 completion gate
```

의도가 명확하고 되돌릴 수 있으며 현재 사실이 충분하면 이 경로를 쓴다. STRICT 위치라는 사실만으로 별도 정찰·설계·교차검토 절차를 추가하지 않는다. 다만 해당 STRICT 행동 테스트·정확성·보안·검증 규칙은 그대로 적용한다.

### 물질적·고위험 경로

```text
read-only 정찰 → 필요한 설계 권한 → build → 비례적 검수·runtime 검증 → completion gate
```

되돌리기 비싸거나 비가역이고, 사실이 물질적으로 불확실하거나, 동결 계약이 요구하는 작업에는 이 경로를 쓴다. **한 단계 = 한 관심사**로 기능과 규칙 변경을 섞지 않고, 커밋은 사람이 명시적으로 허가한 워크플로에서만 논리 단위로 분리한다.

## 교차검토 판정 — 언제 에이전트가 서로 검토하나

다른 에이전트의 검토를 받을지 정하는 기준:

> **(a) 잘못되면 물질적 결과가 있고, + (b) 책임 에이전트가 자기 증거만으로 정확성을 확립할 수 없을 때 → 받는다.**
> **단순하거나, 가역적이거나, 현재 증거로 자명하게 확립할 수 있으면 → 생략한다.**

**(a) 판정 주의 — 스텝 강도는 스텝 이름이 아니라 *건드리는 대상별*로 본다.** "이번은 UI 스텝이라 NORMAL"처럼 뭉뚱그리면, 그 안에 섞인 고위험 조각(예: 결제 멱등키 생성, 금액 계산 공유)을 놓친다. 반대로 STRICT 위치만으로 절차 강도를 자동 증폭하지 않는다. 실제 위험과 동결 계약이 경로를 정한다.

**받을 때의 방식**:
- **좁혀 묻는다.** 열린 "개선점 있어?"는 금지 — 스코프를 부풀리고 과설계를 부른다. 대신:
  - *정합성*: "이 가정이 코드와 맞나" (계획 X → 실제 Y)
  - *접근법*: "이 설계가 이 코드베이스/구조에서 최선인가" (현 계획 vs 대안 + 근거)
- **검토 결과는 *입력*이지 최종 결정이나 새 권한이 아니다.** 받은 제안을 범위·보장·최소 충분 구조에 맞는지 거르고, 최종 권한 판단은 사람이 한다.

**받을 케이스 예** (과거 세션 실제): 포트 시그니처 확장, finalizer 첫 수정, 검증 추상화(helper) 설계, "내가 코드 못 봐서 가정한 인자 모양".
**안 받을 케이스 예**: 줄 정리 같은 위생, 이미 정찰한 영역의 사소한 후속, 가역적 NORMAL UI.

MODEL_COMPENSATION과 그 마찰 판정의 SSOT는 `AGENTS.md`의 현 모델 세대 어댑터다. 공통 원칙은 [Mira AI Engineering Governance v0.1](./engineering/ai-engineering-governance-v0.1.md), 물질적 고위험 overlay는 [Mira Backend / High-Risk Engineering Governance v0.1](./engineering/mira-backend-high-risk-governance-v0.1.md)을 따른다. 이 문서에 마찰 질문을 복제하지 않는다.

## 핵심 엔지니어링 규칙

- **"verify 초록 ≠ 작동."** STRICT 코어·실거래 경로는 *런타임*으로 검증한다(브라우저 클릭, Network status, DB 조회). 타입체크·테스트 통과만으로 "된다"고 하지 않는다.
- **규칙(헌법) 변경은 기능 커밋과 분리** + 변경 전 합의. 저장소 전역 코드 구조 정책의 SSOT는 `AGENTS.md` §4다. 파일·함수 길이와 LOC는 수용·거절 기준도 검토 신호도 아니며, 사용자가 줄 수 정보를 명시적으로 요청하지 않는 한 준수 여부나 “크지만 허용”이라는 방어를 계산·보고하지 않는다. 길다는 이유만으로 코드를 분해·압축하거나 크기를 줄이기 위한 pass-through wrapper·인위적 모듈 경계를 만들지 않는다. 분해는 독립적으로 변경되는 소유권·수명주기, 중복된 도메인 권한·진실 원천, 의존성 방향 문제, 실질적으로 다른 fixture·환경·데이터베이스·cleanup 소유권, 무관한 로직이 transaction·실패 흐름을 가리는 문제처럼 구체적이고 독립적으로 의미 있는 책임·응집성 결함이 있을 때만 제안한다.
- **STRICT 흐름과 DAMP 테스트도 책임 경계로 분해를 판단한다.** 결제·환불 등 고위험 흐름은 응집된 구현이 크더라도 lock·write·rollback·idempotency·evidence 동작을 눈에 보이게 보존한다. DAMP 테스트는 하나의 lifecycle·truth table·fixture 소유자·cleanup 계약을 표현하면 함께 둘 수 있고, 이 소유권이나 계약이 실질적으로 다를 때는 그 책임 결함을 근거로 분해할 수 있다. 독립적으로 의미 있는 재사용 계약의 추출과 구체적인 복잡도·의존성 결함의 지적도 허용된다.
- **외부 API 사실은 공식 문서만.** 2차 블로그 금지. 인용 시 출처 명시. 불확실하면 추측 말고 문서 확인.
- **커밋 규율**: 사람의 커밋 권한이 있을 때만 논리 단위로 분리한다. 기능/스키마/규칙을 한 커밋에 섞지 않는다.
- **고위험 코어 변경 규율 + 레거시 컷오버 기록**: 핵심 트랜잭션(신 결제 finalizer 등)은 물질적 고위험 경로로 다루고, 변경은 최소 단위로 원자성·불변식을 행동 테스트와 런타임 검증으로 고정한다. 구 FROZEN 존은 컷오버 완료로 소멸했으며, 잔존 규칙은 레거시 부활 금지다. 상세 SSOT는 `AGENTS.md` §4.5·§8이다.
- **고정 산출물 저장 지시는 원문을 동봉한다(v3 신설).** 채팅에서 검수·승인된 문안을 에이전트에게 파일로 저장시킬 때, "직전 보고"류의 컨텍스트 참조에 기대지 말고 **원문 전문을 프롬프트에 동봉**하거나, 그게 불가하면 **저장 직후 원문 대조 검수를 절차에 포함**한다. 에이전트 컨텍스트는 지속이 보장되지 않으며, 유실 시 에이전트가 "복원"으로 메우면 검수받지 않은 산출물이 승인된 것처럼 저장된다. (에이전트가 유실·복원 사실을 고지하는 것은 올바른 행동이고, 이 규칙은 지시 설계 쪽 결함을 막는다.)
- **코드를 직접 확인하지 않은 설계·검수 에이전트는 단정 대신 정찰로 위임한다.** 코드 사실을 모르는 채 "이렇게 구현하라"고 단정하면, 그 지시가 실행 맥락(트랜잭션 시점·데이터 신선도·격리)과 어긋나도 못 잡는다. 그런 지점은 "이걸 정찰해 판단하고 근거를 보고하라"로 열어 위임한다 — 구현 에이전트가 능동적으로 근거를 대면 어긋남이 빌드 전에 드러난다. ("재사용하라"류도 같은 값이 *같은 시점·같은 데이터*로 쓰이는지 다르면 틀린다 — 정의는 공유, 접근은 분리.)
- **STRICT/NORMAL 존, 레거시 컷오버 기록, 책임·응집성 정책, 추상화 계층의 SSOT는 `AGENTS.md`**(와 `eslint.config.mjs`)다. 특히 저장소 전역 코드 구조 정책은 `AGENTS.md` §4가 소유하며, 이 프로토콜은 독립적인 수치 크기 체계를 정의하지 않는다. 협업 검토는 LOC가 아니라 구체적인 책임·소유권·의존성·트랜잭션 가시성 결함을 지적할 수 있다.

## 검수 기준 (Claude가 결과를 볼 때)

- **"왜"를 확인한다.** 에이전트 보고를 결론만 받지 않는다 — 수치/동작이 왜 그런지(예: 테스트 카운트가 왜 그대로인지, 왜 이 상태로 전이했는지) 짚는다.
- **고위험 코어는 diff를 눈으로.** 보고가 "불변"이라 해도, 되돌리기 비싼 코어(finalizer 등)는 직접 본다. 레거시 부활 금지 대상에 diff가 있으면 명시적 사람 권한과 근거가 없는 한 검수 실패 신호다.
- **런타임 증거를 요구.** 고위험 런타임·실거래 경로는 "무엇을 클릭했고 어떤 status를 봤고 DB가 어떻게 변했나"를 보고에 요구한다. (자동화가 막히는 단계 — 예: 카드사 보안 키패드 — 는 사람이 1회 수동 검증.)
- **회귀 신호.** 기존 테스트 수가 유지/증가하는지로 회귀 없음을 1차 확인하되, 그것에만 의존하지 않는다.

## 새 개발 채팅 시작 패턴

1. **이 문서 + 최신 핸드오프 문서**를 붙인다 (규칙 + 맥락). 핸드오프엔 *결정의 근거*와 *다음 계획*이 담겨 있어야 한다(코드 정찰로는 복원 안 되는 것들).
2. 작업의 위험·가역성·사실 불확실성과 동결 계약을 확인해 단순·가역 경로 또는 물질적·고위험 경로를 고른다.
3. 선택한 경로의 build와 검증을 수행하고, 커밋은 사람 권한이 있을 때만 한다.

> Codex 쪽은 `AGENTS.md`가 자동 적용되므로 별도 첨부 불필요. ChatGPT/Claude 쪽은 이 문서로 충분하되, 필요 시 `AGENTS.md` 전문을 붙인다.

## 적용 범위 메모

이 프로토콜은 **개발 / 에이전트 협업 채팅**에 적용된다. 같은 프로젝트라도 소프트웨어 엔지니어링이 아닌 작업에는 자동 적용하지 않는다. 저장소에서 실행되는 소프트웨어 작업의 범위 라우팅과 핵심 규칙은 `AGENTS.md` 및 위 두 계층형 거버넌스 문서가 소유한다.
