## 0. 공통 전제 블록 (두 문서 공유 — 여기만 읽어도 배경이 성립)

- **시스템 전제:** 단일 DB · 단일 창고 · 출시 규모 트래픽. 주문/결제/제작이 초기에는 같은 앱·같은 DB에 존재한다(자체 제작, 아래 CORE-1·MFG-1). 결제·주문 코어는 자체 구축(ARCH-0). DB 엔진 = **PostgreSQL**, 트랜잭션 격리 수준 = **READ COMMITTED**(ARCH-1 — 격리 수준은 논의 §9 잠금 설계의 전제라 엔진과 함께 확정). 호스팅(관리형 vs 자체 운영)은 별도 미결(코드 불변이라 비차단).
- **출시 범위:** 글로벌 커머스, 1차 동시 출시 시장 = **한국·미국·일본**(SCOPE-2). 세금·통화·관세·MoR 등 글로벌 종속 항목이 전부 활성.
- **상품 구성:** 재고형(STOCKED)과 맞춤제작(MTO)을 함께 판매(SCOPE-3), 한 장바구니 혼합 결제 허용(SCOPE-4).
- **결제 코어 골자:** 주문은 결제 성공 후 생성한다(Full C, CORE-1a). 결제 전 단계 캐리어는 CheckoutSession. 완료 로직은 confirm(동기)·웹훅(백업)이 공유하는 단일 트랜잭션(CORE-6).
- **용어:** *세션* = CheckoutSession(결제 전 장바구니 스냅샷 보유체). *MR* = ManufacturingRequest(제작 작업지시 + 제작 상태 보유체). *망취소* = 결제는 성공했으나 주문 성립 조건 불충족 시 결제를 되돌리는 것. *축 M* = 재고형/주문제작 제조 구분. *축 R* = 재판매 가능성(→ 청약철회 배제 성립 여부).
- **이 문서의 근거 한계:** "확정"의 근거는 사용자 발화와 그 논리적 귀결이며, 실제 스키마·코드·PG 계약·법률 요건으로 검증된 것이 아니다. 외부 사실(관세·PG 스펙 등)은 표기된 검증 시점 기준이며 계약·구현 단계 재확인 대상.

## ARCH. 구축 방식·인프라 의미론 (모든 CORE·MFG의 선행 결정) — v4 신설

### ARCH-0. 결제·주문 코어 = 자체 구축 (build)
- **상태:** 확정 (이번 승인 — 초안은 2026-07-05 검토의 사후 재구성 레코드였고, 사용자 승인으로 근거 ①이 추가되어 확정 승격)
- **결정:** 결제·주문·제작 코어(세션·완료 트랜잭션·Order·MR·대사)를 자체 구축한다. SaaS 커머스 플랫폼 전면 채택, MoR 통합형 플랫폼은 지금 채택하지 않는다. **범위 한정:** 이 레코드는 결제·주문 코어에 관한 것이며, 결제 밖 영역(카탈로그·어드민·프론트)의 기성 골격 채용은 막지 않는다(별도 결정).
- **맥락·전제:** 이 문서의 모든 확정(CORE-1~6, MFG, 논의 §9)은 자체 스키마·자체 트랜잭션 경계를 전제로 논증되었으나, build 자체의 결정 레코드가 없었다. 첫 커밋이 곧 매몰 시작이므로 코드 전에 명시 확정한다. **승인 시점의 정보 한계(인지된 채 승인):** 팀 규모·목표 기한은 미확인 상태이며, 이 두 값만이 결론을 (a) 쪽으로 뒤집을 수 있는 변수다. "1~2인 + 기한 3개월 이내"급 조합으로 판명되면 승인 재확인 대상(만료조건 ③과 연동).
- **검토한 옵션과 이유:**
  - (a) SaaS 커머스 + MoR 통합(Shopify Managed Markets류) — 배제: ①플랫폼이 MoR을 대행하는 구조는 MOR-1이 배제한 구조 C·D의 재도입(수수료·MTO 반품 정책 충돌·종속). ②MTO 특수성(MR·착수 게이트·축 R 라인별 판정·제작 상태 노출)이 표준 주문 모델 밖 → 커스텀 우회 시 코어 로직 자체 구현 + 플랫폼 제약의 이중 부담. ③확정 불변식(Full C·공유 단일 트랜잭션·행 잠금)을 플랫폼 위에서 강제할 수 없음. 단 논의 §7.2/7.3(다통화·세금·관세) 상당 부분을 플랫폼이 흡수하는 이점은 실재하며, 이것이 만료조건의 근거다.
  - (b) 헤드리스/오픈소스 커머스 위 커스터마이징 — 결제 코어에 한해 배제: 결제 코어는 어차피 본 문서 명세대로 재작성해야 해 절감분이 결제 밖에 국한. 결제 밖 채용은 위 범위 한정대로 열어 둠.
  - (c) 자체 구축 — **채택.** 확정 스택과의 정합, MTO 특수성, MOR-1 정합.
  - (d) 결제 통합만 오케스트레이션 위임 — 배제, 논의 §7.7 도입 옵션 (iv)에 등재(상호참조).
- **근거 출처:** ①(이번 승인) + ④(옵션 비교 논거) + ②((a)-①은 MOR-1로부터의 귀결)
- **의존·파급:** 전 CORE·MFG 레코드가 이 위에 있음. Track 1 착수의 선행 게이트(Phase 0-③) — 본 확정으로 해소.
- **만료조건(논의 §12 등재):**
  - ① 결제 코어 구현 지연이 **N = min(목표 일정의 1/3, 절대값 2개월)** 초과 시 (a) 재비교. 이 값 규칙(1/3·2개월)은 검증된 수치가 아닌 휴리스틱(④)이며, 목표 출시일 확정 시 실제 날짜로 치환한다.
  - ①′ **선행 지표(권장 주 트리거):** Stage B2+C1(완료 트랜잭션 + 동시성 하네스 통과)이 착수 후 **[전체 일정의 1/4]** 시점까지 미완이면 재검토 발동 — "출시일 N개월 초과"는 끝에서야 발화하는 늦은 트리거라, 난이도 집중 구간(B2+C1)의 속도를 선행 지표로 쓴다. 1/4도 휴리스틱(④).
  - ② MOR-1 만료(해외 물량 급증으로 MoR 재검토) 발동 시 함께 재부상 — (a)의 최대 걸림돌이 MoR 구조이므로.
  - ③ 팀 역량·리소스가 논의 §14 최소 컷 수행에 미달로 판정.
- **미기재 값(사용자 입력 필요):** 목표 출시일(①·①′의 괄호를 날짜로 치환), 팀 규모·경험(③ 판정 및 승인 재확인 조건).

### ARCH-1. DB 엔진 = PostgreSQL · 격리 수준 = READ COMMITTED
- **상태:** 확정 (이번 승인) — 이 레코드는 **의미론(엔진·격리 수준)만** 확정한다. 호스팅(관리형 vs 자체 운영)은 별도 미결: 스키마·잠금 설계가 의존하는 것은 의미론이고, 호스팅은 나중에 바꿔도 코드가 안 바뀐다.
- **결정:** PostgreSQL. 기본 트랜잭션 격리 수준 READ COMMITTED. **격리 수준을 함께 명시하는 이유:** 논의 §9의 행 잠금 + 유니크 설계는 READ COMMITTED를 암묵 전제한다(SERIALIZABLE이면 직렬화 실패 재시도 로직이 별도 필요해 설계 자체가 달라짐). 이후 격리 수준 변경은 이 레코드 개정 + §9 재설계 없이는 금지 — 명시하지 않으면 누군가 격리 수준을 올리다 완료 트랜잭션(B2)이 조용히 깨진다.
- **검토한 옵션과 이유:**
  - **(a) PostgreSQL — 채택.** SELECT…FOR UPDATE(논의 §9)·복합 유니크(논의 §2.2)는 기본. 그 위에 ⑴ **트랜잭션 DDL** — A2가 "마이그레이션 전제"인데 실패 시 원자 롤백이 되어, 스키마가 여러 번 바뀔 프로젝트 초기와 직결. ⑵ **JSONB** — 논의 §1.1 스냅샷의 미확정 필드를 "확정분 컬럼 + 미확정분 JSONB"로 두어, 스키마 동결 게이트를 지키면서 골격 진행 가능. ⑶ **FOR UPDATE SKIP LOCKED** — A3 outbox 워커의 표준 패턴. ⑷ READ COMMITTED에서의 잠금 동작이 단순해 §9의 "데드락 위상 깨끗" 논증이 그대로 성립.
  - (b) MySQL/InnoDB — **배제(조건부).** 확정 설계가 InnoDB에서 불가능한 건 아니나 상대 열위: 트랜잭션 DDL 부재(마이그레이션 중단 시 반쯤 적용된 스키마), REPEATABLE READ 기본값의 갭 락이 insert 밀도 높은 유니크 검사 워크로드에서 예상 밖 데드락을 만드는 알려진 함정(격리 하향으로 완화되나 팀 학습 부담 증가), JSONB 대비 약한 JSON 인덱싱. **뒤집는 조건(미해소):** 팀이 MySQL 운영 숙련이 깊고 Postgres가 처음이면 (b)가 이긴다 — 결제 시스템에서는 엔진의 이론적 우위보다 "새벽 장애 때 팀이 아는 엔진"이 더 큰 안전장치이기 때문. 만료조건 ①로 등재.
  - (c) NewSQL(CockroachDB류) — 배제: 분산 직렬화 의미론이 §9 잠금 논증과 다르게 동작하고(재시도 전제), 출시 규모(단일 DB, §0)에서 얻는 게 없음. 재검토 시점은 논의 §12 서비스 분리 트리거와 같은 층.
  - (d) NoSQL — 배제: 유니크 제약·다행 트랜잭션·행 잠금이 확정 설계의 하중 지지벽이라 논외.
- **근거 출처:** ①(이번 승인) + ④(엔진 의미론 비교는 학습 지식 — 시점 비민감 사실이라 검색 미사용, 벤치마크·실측 아님)
- **의존·파급:** 논의 §9(잠금 전제 해소)·§2.2(유니크)·§2.3(outbox SKIP LOCKED)·§1.1(컬럼+JSONB 전략), Track 1 A2 DDL의 전제. 논의 §13 "DB 엔진" 플래그 해소.
- **만료조건:** ① 팀 DB 경험 확인 결과 "MySQL 깊음 + Postgres 전무"로 판명 → 코드 착수 전에 한해 (b) 재비교. ② 격리 수준 상향 필요 제기 → §9 재설계와 동반 개정. ③ 분산 필요(논의 §12 서비스 분리) → (c) 재검토.
- **미기재 값(사용자 입력 필요):** 팀의 DB 운영 경험 한 줄(만료조건 ① 해소용).

### ARCH-2. 레거시 결제 코드 처분 = 재작성 + 클린 컷 + 제자리 동결 (v5 신설)
- **상태:** 확정 (2026-07-06, 사용자 — 결정 3건: 재작성 채택 / 실배포·실결제 이력 없음·기존 Order/Payment 행 폐기 승인 / B′ 동의)
- **결정:** 기존 구현(mira 레거시 결제·주문생성 코드)은 본 정책의 구현체로 개조하지 않고 **재작성**한다. 레거시는 **제자리 동결(FROZEN)** 후 **컷오버 커밋에서 일괄 교체**(코드 삭제 + 구 테이블 drop — 클린 컷). 인양 가치는 코드가 아니라 문서(`legacy_salvage_notes.md`)로 이전한다.
- **맥락·전제:** 정찰 2건으로 확인된 레거시↔정책 갭이 조각이 아니라 골격이다 — 결제 전 PENDING Order(CORE-1이 배제한 A패턴), Payment 유니크 단일(idempotencyKey — §2.2 미충족), 행 잠금 부재(§9), MR 결제 전 전 라인 생성(MFG-1 위반), 웹훅 raw 미저장(§7.5). 클린 컷의 성립 조건 = 실사용자·실결제 배포 이력 없음(사용자 확정).
- **검토한 옵션과 이유:** (a) 점진 리팩터 — 배제: 골격 분기라 STRICT 코어를 반복 개봉하는 최악 경로. (b) 스트랭글러 병행 — 배제: 실데이터 없음 + 신·구 스키마가 동명 모델(Order 등)·상반 의미론이라 공존 불가 → 병행이 B2 전에 강제 종료. (c) 레거시 이동(payment-legacy) 후 동결 — 승인 후 철회: (b) 배제와 같은 이유로 병행 가치가 소멸해 이동은 순수 churn. (d) **제자리 동결 + 컷오버 게이트(B′) — 채택.**
- **근거 출처:** ①(사용자 확정 3건) + ②(동명 모델 공존 불가는 스키마 논리의 귀결) + ④(옵션 비교·정찰 해석)
- **의존·파급:** 집행 규칙(동결 글롭·예외·컷오버 게이트 조건)의 SSOT는 **`AGENTS.md` §4.5**(여기 중복 기재 안 함). Track 1 A2가 컷오버 직후 canonical 경로·모델명을 백지 인수. 컷오버의 테이블 drop은 `migrate deploy` 경유로 프로덕션 DB에도 적용 → go-live 체크리스트 "행 폐기 인지" 항목.
- **만료조건:** 컷오버 완료 시 이 레코드는 이행 종료(역사 기록화). 컷오버 전에 실결제·실사용자가 발생하면 클린 컷 전제 붕괴 → (b) 재검토.

## A. 결제 코어 아키텍처

### CORE-1. 주문 생성 시점 = 결제 성공 후 (Full C)
- **상태:** 확정
- **결정:** 주문(Order)은 결제 성공 후 생성한다. 결제 전 단계의 캐리어로 CheckoutSession을 둔다. A(체크아웃 시 PENDING Order)도 A′(경화판)도 아니다.
- **맥락·전제:** 결제 전에 영속 Order를 만들면, 이탈한 체크아웃마다 버려진 주문 레코드가 쌓여 주문 공간이 오염된다. Full C는 "성공한 결제만 주문이 된다"로 이 오염을 원천 차단한다.
- **검토한 옵션과 이유:** (A) 체크아웃 시 PENDING Order — 배제: 오염 비용이 영구·분산적. (A′) PENDING의 경화판 — 배제: A를 안 쓰면 A′의 존재 이유도 소멸. (C) 결제 후 생성 — **채택**.
- **근거 출처:** ①(이전 대화 확정 원문)
- **의존·파급:** MR 생성 시점(MFG-1), 세션 스냅샷 명세(논의 §1.1), 지연완료 수단 배제(CORE-5·논의 §8.2)가 전부 이 결정에 종속.

### CORE-2. CheckoutSession = 백지 신규 정의 (v4 문구 개정 확정)
- **상태:** 확정 (구 논의 §1.2의 개정 제안을 이번 승인으로 확정 — §1.2는 이관 종료)
- **결정:** 현 Order를 개명하지 않고 세션을 새로 정의한다. Order 설계는 **입력으로만** 취급해 라인아이템·금액만 차용한다. 이행 필드 배치(개정 문구): **이행 *상태*(운송장·배송/제작 진행)는 Order로, 이행 *입력*(배송지·배송방법·수령인)은 세션 스냅샷으로.**
- **맥락·전제:** 기존 Order 스키마를 재활용(개명)하면 결제 전/후 의미가 한 테이블에 섞여, Full C가 없애려던 혼재가 되살아난다. 문구 개정의 강제 근거: 웹훅 경로는 브라우저 없이 주문을 만들므로(CORE-1+CORE-6의 귀결) 주문 생성의 전 입력이 세션에 있어야 성립한다.
- **검토한 옵션과 이유:** (a) 개정 문구 채택 — **채택.** (b) 이행 입력도 Order에만 — 배제: 웹훅 경로가 입력 부재로 주문을 못 만들어 백업 경로가 2등 시민화 → confirm 실패 복구가 대사로만 밀려 불변식 1(논의 §3)의 실시간성 상실. CORE-6의 두 진입점 대칭을 포기하지 않는 한 선택 불가. (c) 웹훅이 입력 미비 시 임시 주문을 만들고 나중에 채움 — 배제: Full C가 없앤 미완성 주문 오염의 재도입.
- **파생 규칙(함께 확정):** PAID 후 이행 *입력* 변경(배송지 오타 등) 처리 — ⑴ 스냅샷은 불변 유지(증빙), ⑵ Order에 오버라이드 필드 + 변경 이력을 둔다(Track 1 A2 스키마에 자리 예약 필요 — 지금 함께 닫는 이유), ⑶ 세액·배송비가 배송지에 종속되는 관할에서 **금액이 바뀌는 변경(국가/과세구역 이탈)은 불허**.
- **근거 출처:** ①(이번 승인) + ②(웹훅 단독 생성의 성립 조건)
- **의존·파급:** 이 확정으로 세션 스냅샷에 배송지·수령인 등 **PII 포함이 확정** → 논의 §1.3(PII 볼트) 결정의 압력·시급성 증가(인지된 채 승인 — §1.3 자체는 여전히 미확정). 논의 §1.1의 "배송지 값 복사" 행은 권고에서 확정 원칙으로 승격(스냅샷 명세 전체·필드 상세는 여전히 §1.1 미확정).

### CORE-3. §3 안전장치 4개 (Full C의 전제조건)
- **상태:** 네 장치의 **존재**는 확정 / 각 세부 강화는 미확정(논의 §2)
- **결정:** (a) 세션은 결제 개시 시점에 불변 스냅샷으로 동결. (b) paymentKey·세션 id에 유니크 제약을 걸어 멱등 주문 생성(정확히 1개). (c) Payment 저장 + Order 생성을 같은 트랜잭션. (d) PG 내역 ↔ 주문 대사(reconciliation) 배치.
- **맥락·전제:** Full C에서 "결제 성공 → 주문 생성"이 네트워크·재시도·동시성 속에서도 정확히 1회 일어나려면, 동결·멱등·원자성·사후검증의 네 축이 동시에 필요하다. 하나라도 빠지면 이중 주문·유령 결제·금액 조작 창이 열린다.
- **근거 출처:** ①(존재) / 세부는 논의 문서로 이관
- **의존·파급:** (b) 복합키·이중 유니크, (a) 라인별 배분, (c) 트랜잭션 경계, (d) 양방향·정산 대사 — 전부 논의 §2. 멀티 PG 확정(PG-2)으로 (b)의 복합키 `(provider, paymentKey)`가 미래 대비에서 출시 요건으로 승격.

### STOCK-임시. 전 라인 MTO 카탈로그에서 stock = 임시 수량 쿼터 (v6 신설, 임시 규정)

## MFG. 제작 흐름 — 이번 대화 확정 (자체 제작)

### MFG-1. MR 생성 시점 = PAID 트랜잭션 내
- **상태:** 확정 (이번 대화)
- **결정:** ManufacturingRequest는 **결제 완료(PAID) 트랜잭션 안에서** MTO 라인 단위로 생성한다. 초기 상태는 '착수 전'으로 두어 착수 시점(논의 §4-1)과 분리한다. 공장 통지·스케줄링 등 진짜 부수효과만 outbox 이벤트로 뺀다.
- **맥락·전제:** "MR을 언제 만드나"는 두 전제를 깔고 있었다 — ①MR이 커머스 DB 엔티티다, ②'생성'이 한 사건이다. 이를 풀면 MR이 담는 정보가 **커스터마이징 구성**(결제 전 확보·동결, 금액 산정 입력)과 **작업 지시**(PAID 후에만 의미)로 갈린다. 구성 데이터는 세션 라인 + 스냅샷이 이미 충족하므로, 진짜 질문은 "작업 지시 엔티티를 언제 만드나"로 좁혀진다.
- **검토한 옵션과 이유:**
  - 세션 단계 생성(dormant) — 배제: 이탈 세션만큼 버려진 MR이 쌓여 CORE-1이 없앤 오염이 재발.
  - 결제 개시(동결) 시점 생성 — 배제: 결제 실패율만큼 여전히 쓰레기. 어중간.
  - **PAID 트랜잭션 내 행 생성 — 채택:** "PAID MTO 라인 ⇒ MR 정확히 1개" 불변식이 트랜잭션 원자성으로 공짜 보장. 자체 제작 = 같은 DB이므로 성립. 비용: 결제 트랜잭션이 제작 테이블에 결합(서비스 분리 시 만료), MR insert 실패가 망취소로 전파(단 Order insert 실패와 같은 버그 클래스라 수용).
  - PAID 후 outbox 워커가 생성 — 차선: 분리엔 유리하나 "PAID인데 MR 없음" 창이 생겨 불변식이 대사 검사 대상으로 강등. 단일 서비스 동안 이점 없음.
  - 커머스 DB에 MR 미보유 — 지금 배제(만료조건): 제작이 처음부터 외부 시스템일 때의 정답.
- **근거 출처:** ①(자체 제작·PAID 후 생성 승인) + ④(옵션 비교 논거)
- **의존·파급:** CORE-4를 구체화하고 CORE-2의 "이행 상태는 Order/제작 진행" 배치와 연결. §2.3(부수효과 outbox)와 정합.
- **만료조건:** 제작이 별도 시스템(MES)·외주로 분리되면 → MR을 이벤트 투영으로 전환(위 마지막 옵션). 논의 §12의 "주문/결제 서비스 분리" 트리거에 병합.

### MFG-2. 제작 진행 상태 기록 구조
- **상태:** 확정 (이번 대화)
- **결정:** 제작 상태의 **주인은 MR**. MR에 내부 상태(공정 단계는 지금 고정하지 않고 운영하며 변경 가능)와 담당·메모를 둔다. 상태 변경 시마다 **append-only 전이 이력 테이블**에 (from, to, actor, 시각, 메모) 기록. **고객 노출 상태**는 내부 상태→고객 단계 **매핑표**로 도출하며, 소수(3~5개)의 안정적 단계로 둔다. OrderLine에는 캐시하지 않고 조회 시 계산으로 시작(출시 규모 충분, 필요 시 캐시 추가).
- **맥락·전제:** "어디에 기록하나"는 ①기록 장소가 하나다, ②'진행 상태'가 한 종류다, 를 전제한다. 풀면 — 진실은 하나·노출은 투영으로 분리 가능하고, 상태는 **내부 운영용**(세분·가변·담당/메모 포함)과 **고객 노출용**(소수·안정·사실상 약속) 두 종류다. 한 필드에 합치면 고객이 공정 잡음을 보거나 작업자가 노출 의미론에 묶인다.
- **검토한 옵션과 이유:**
  - OrderLine 상태 컬럼 직접 — 배제: 이력 부재, 주문 테이블이 제작 도메인에 오염.
  - **MR이 상태 주인 — 채택:** 작업지시 엔티티가 상태를 갖는 게 자연스럽고 MFG-1과 직결.
  - 이벤트 소싱(전이만 진실, 현재는 프로젝션) — 무거워 배제하되, 가벼운 형태(현재 상태 컬럼 + append-only 이력 병행)를 채택안에 흡수.
  - 별도 도구(스프레드시트) — 배제: 고객 노출 요구 순간 수동 동기화 지연·불일치가 고객에게 노출. (과도기엔 "DB 직접 갱신 초간단 어드민"이 타협점.)
- **근거 출처:** ①(자체 제작·상태 노출 채택) + ③(주문제작 도메인 진행노출 관행) + ④(구조 논거)
- **의존·파급:**
  - 착수 전이 이벤트가 논의 §4-1 **point of no return**을 기록 → 취소 가능 판정이 이 상태 참조. 취소요청↔착수 레이스는 §9 패턴 재사용(MR 행 잠금 후 재검사).
  - 전이 이력 = 논의 §10 차지백 증빙의 "제작 진행 기록" + §5.2(b) 슬롯 활성 지표(리드타임 실측)의 데이터 소스.
  - 상태 변경 알림은 전이 이벤트 → outbox(§2.3).
  - 혼합 A안(§5.2) "이행 상태기계는 라인 수준"과 정합: 제작 상태는 MTO 라인에만, 주문 수준 상태는 집계로 파생.
- **주의(파급):** 예상 완료일을 노출하면 그것이 약속이 된다. 특히 미국 FTC 통신판매 규칙상 표시 발송기한 초과 시 통지·환불 의무 → 날짜는 버퍼 포함 범위로 표기, 초과 시 자동 통지 훅을 §7.1에 연동(논의 문서에서 상세).

## SCOPE. 출시 범위·상품·시장

### SCOPE-1. (구 B1) 글로벌 커머스로 시작

- **상태:** 확정 (이번 대화)
- **결정:** 1차 동시 출시 시장은 KR·US·JP. 통화는 KRW·USD·JPY.
- **맥락·전제:** SCOPE-1(글로벌)을 구체 시장 집합으로 확정. 이로써 통화·세금·관세·철회권 등이 "3개 관할 활성"으로 실체를 갖는다.
- **근거 출처:** ①
- **의존·파급:**
  - **미국:** 소액수입 de minimis 면세는 폐지 상태다(2025-08-29 행정명령 시행 → 2026-06-24 CBP 잠정최종규칙 2건으로 우편·비우편 전 모드 무기한 정지 성문화, 2025-07 OBBBA로 2027-07-01자 법정 폐지 확정). **폐지 자체는 사실상 비가역** → DDP/DDU와 landed cost 표시는 결제 크리티컬 패스(논의 §7.3), SKU별 HTS·원산지는 상품 스키마 요건. 단 **세율·부가 관세 체계는 유동적**(2026-02 행정명령으로 일부 IEEPA 관세 종료 등)이라 출시 시점 재확인 필수. **우편망 경유엔 신설 우편 약식통관 절차가 별도 적용** → 출고 채널(우편 vs 특송)이 통관 경로·데이터 요건을 가른다(논의 §7.3). 관세와 별개 축으로 **주 판매세 economic nexus**가 존재한다(논의 §7.3 신설).
  - **일본:** 온라인 3DS 2.0 의무·JCB J/Secure 2.0, 특정상거래법 표기·일본어·엔화 표기가 사이트/PG 심사 요건(논의 §7.3·PG-2). 편의점 결제는 지연완료 수단이라 CORE-5·§8.2 경계와 연쇄(논의 §8.2·PAY-JP).
  - **한국:** Toss로 국내 충분. 수출분 부가세 영세율은 세무 확인 대상.
  - 통화 KRW/USD/JPY → 논의 §7.2(JPY 0자리 라운딩) 실전화, 환불 환손실 부담 정책 §7.1에 추가.
- **근거(외부):** ③ — de minimis 폐지·미국 관세 체계 변화는 2026-07 검색 확인(수치는 유동적이라 미인용). 일본 3DS 의무·JCB·특정상거래법은 ③.

## MFG-M / MFG-R. 맞춤제작 유형과 축

사용자 정의 두 유형:
- **유형 1:** 기본 틀을 고르고, 그 위에서 선택 가능한 표준 옵션을 조합해 주문.
- **유형 2:** 옵션을 선택하고, 그 옵션의 세부 사항을 (선택 가능한 스펙트럼 안에서) 조절해 주문.

### MFG-M. 축 M(제조) — 두 유형 모두 MTO
- **상태:** 확정
- **결정:** 두 유형 다 주문 전에는 완제품이 없고 주문 후 제작되므로, 재고·제작 의미론(CORE-4 MR, 제작 후 이행, 재고 차감 아님)이 두 유형에 동일 적용.
- **맥락·전제:** 사용자의 정의에서 직접 강제되는 귀결.
- **근거 출처:** ①+②
- **만료조건:** 옵션 체계 밖 완전 주문제작(상담형)이 추가되거나, 반대로 인기 표준 조합을 선제작(MTS)으로 돌리면 → 축 M 재검토(논의 §12에 양방향 트리거). **(v6)** MTS 전환은 STOCK-임시의 stock 의미도 재활성화(임시 쿼터→실재고).

### MFG-R. 축 R(재판매 가능성 → 철회 배제)
- **상태:** 미확정 (법률 종속)
- **결정:** 유형 2의 "스펙트럼"이 이산(열거 눈금)인지 연속(범위 내 임의값)인지에 따라, 그리고 관할별 철회권 규정에 따라 갈린다. 논의 §6 + 법률 검토.
- **근거 출처:** 논의 문서로 이관
- **의존·파급:** SCOPE-2로 관할이 KR·US·JP 3개 → 판정표가 (라인 속성 × 배송지 관할) 2차원(논의 §6·§7.1).

## MOR / PAY / PG. 정산 주체와 결제 인프라 — 이번 대화 확정

### MOR-1. MoR/계약 주체 = 한국 법인 단일
- **상태:** 확정 (이번 대화)
- **결정:** 한국 사업자(법인) 단일을 MoR·계약 주체로 유지하고, 해외는 크로스보더 PG로 매입한다. 해외 법인 설립·해외 MoR 대행은 지금 채택하지 않는다.
- **맥락·전제:** 단일 창고에서 어차피 크로스보더 출고이고, 초기 물량에서 해외 법인 고정비·MoR 대행 수수료가 이득을 상회. 이 선택의 대가는 **낮은 크로스보더 카드 승인율과 세금·관세 직접 처리**이며, 이를 인지하고 채택한 결정이다.
- **검토한 옵션과 이유:**
  - **구조 A. 한국 법인 + 크로스보더 PG — 채택.** 고정비 최소, 런칭 속도.
  - 구조 B. 현지 법인 + 로컬 어콰이어링(Stripe/Adyen 등) — 배제: 승인율·청구표기·세금도구 우위나 설립·세무 고정비 큼. **만료조건:** 시장별 매출·승인율 실측이 임계 초과 시 재부상.
  - 구조 C. 크로스보더 MoR 대행 — 배제(기존 이분법에 없던 제3안, 기록): 수수료 무겁고 MTO 반품·분쟁이 대행 표준정책과 충돌 소지.
  - 구조 D. 해외는 마켓플레이스 병행 — 범위 밖(자사몰 전제), 헤지로 존재만 기록.
- **근거 출처:** ①(한국 법인 유지·"물리 상품 받쳐줄 MoR 못 찾음") + ④(배제 근거 교정)
- **배제 근거 교정(중요):** "물리 상품 MoR이 없어서"로만 적으면 만료 트리거가 죽는다. 정확히는 — 유명 MoR(Paddle·FastSpring류)은 디지털 전용이라 부적합이 맞고, 물리 상품 크로스보더 MoR도 존재하나(Global-e·ESW·Shopify Managed Markets류) 규모 요건·플랫폼 종속·MTO 반품 정합성 때문에 현 단계 부적합.
- **의존·파급:** 논의 §7.2 확장·§7.3(세금·관세) 착수 가능해짐(논의 §12 "MoR 확정" 트리거 발동). 아래 PG 스택이 전부 이 결정을 전제.

### PG-1. 시장별 복수 PG 허용
- **상태:** 확정 (이번 대화)
- **결정:** 한 국가에 복수 PG를 선택 가능하게 설계한다. 시장→PG 1:1이 아니라 **(시장 × 결제수단 × 통화) → PG 라우팅 표**로 둔다. **(v5)** 표의 각 행에는 **완료 시맨틱(동기/지연) 속성을 필수 열**로 둔다 — 지연완료 여부는 수단 단위가 아니라 (PG × 수단 × 처리 경로) 단위에서 갈리기 때문이다(예: PayPal 내 eCheck 경로, 논의 §8.2). 이 열이 §8.2 설계 경계의 검사 지점이다.
- **맥락·전제:** 시장마다 지배적 수단이 다르고(예: 일본은 카드+PayPay+편의점), 한 PG가 그 시장의 모든 수단을 최적 커버하지 못한다. 그래서 배정 단위가 시장이 아니라 (시장×수단)이다.
- **근거 출처:** ①("한 국가에 여러 PG")+②(라우팅 표는 귀결)
- **의존·파급:** 멀티 PG day-one → CORE-3(b) 복합키 `(provider, paymentKey)` 출시 요건화, PG별 대사·정산 대사(논의 §2.4), 웹훅 시맨틱 PG별 분리(논의 §3-불변식5). 라우팅 표 자체는 논의 문서에서 상세.

### VOID-KEY. 보상(void) 멱등키 규약 (v6 신설 — 구현 확립, 정책 추인)
- **상태:** 확정 (2026-07-06 — Stage B 구현 확립)
- **결정:** 완료 실패 시 보상(pg.void) 명령의 멱등키 = void:{provider}:{providerPaymentKey}. 같은 캡처의 void 인텐트는 이 키로 1개(outbox dedupKey 유니크가 큐잉 멱등). 이 키는 실 PG 취소의 멱등 키(Toss Idempotency-Key·PayPal PayPal-Request-Id)로도 전달(operationKey — D-stage 실 API 멱등).
- **맥락·전제:** 구 Open 공백 보상 공유키의 결정. B2 감마가 이 키로 enqueue, B5 핸들러가 operationKey로 executor 전달.
- **근거 출처:** (4)구현 정합 + (1)설계 시 사용자 승인
- **의존·파급:** Open 2.3 outbox·3-불변식5와 정합. 주의: 완료 실패의 전액 무효화 한정 — 정상 주문 부분환불·운영자 환불 멱등키는 §7.1에서 별도(범위 다름).
- **만료조건:** §7.1 환불 설계가 통합 멱등키 체계를 정의하면 포섭 가능(현재 void 전용).

### PG-2. 초기 PG 스택 (후보)
- **상태:** 방향 확정 / 개별 PG 스펙·최종 선정 미확정
- **결정(방향):** 한국 = **Toss**(국내). 미국 = **PayPal** 중심. 일본 = **카드(JCB 포함) 기본 + PayPay 상위 보강**, PayPal은 보조. 해외 카드 매입·일본 로컬 수단 처리 PG로 **엑심베이 / KG이니시스**를 후보로 검토.
- **맥락·전제:** PayPay는 일본 간편결제 1위(등록 7,300만+, 점유 2/3+)라 일본 결정 요인이나, 일본 이커머스 전체는 여전히 카드가 최대 → "카드 기본 + PayPay 보강" 구조. PayPal은 미국 신뢰 자산이라 미국 중심 재배치.
- **검토(외부 검증):**
  - 엑심베이: 글로벌 카드(VISA/Master/JCB/Amex/Diners/Discover) + 일본 편의점(eContext) + **PayPay**(2026 도입) + Alipay/WeChat/UnionPay, MCP 다통화. 결제수단 범위가 넓음. **단 자사몰 직계약에서의 PayPay 가용 범위는 확인 필요**(도입 사례가 특정 호스팅 채널 기준).
  - KG이니시스: 일본 법인(2021 설립)이 GMO-PG 연동 중개, 엔화 승인으로 카드 승인율↑, 최대 월 6회 원화/엔화 정산. 간편결제 라쿠텐페이·아마존페이·d바라이·au PAY·메르페이 + **PayPay**. 일본결제 심사에 특정상거래법 표기·일본어·엔화 표기 선요구.
- **근거 출처:** ①(후보 지정) + ③(두 PG의 PayPay·수단·정산 검증, 2026-07) + ④(구조 해석)
- **미검증/확인 필요:** 두 후보의 **자사몰 직계약 PayPay 가용성, 수수료(수단·경로별 편차 큼→직접 견적), 정산 통화·주기, 웹훅 서명·재전송·조회 rate limit(§3-불변식5 적용 가능성), 부분환불·환불 시한, 3DS/사기 도구, MTO 분쟁·차지백 취급, **(v5)** 지연완료 경로 존재 여부와 차단 가능성(특히 PayPal의 eCheck·리스크 홀드 PENDING — 계정 수신 설정으로 차단 가능한지·차단 범위), 연동 방식별 PCI DSS 범위(SAQ A 성립 여부).** PayPal에도 동일 항목(특히 커스텀 상품 판매자 보호). Stripe/Adyen은 미검증.
- **의존·파급:** 두 후보 변별 기준이 "PayPay 되냐"(둘 다 됨)가 아니라 위 미검증 항목으로 이동. 최종 선정은 논의 §0의 열린 질문.

## 검토 경계 (이 문서)

- 수록된 것은 결제 코어 경로 + 상품/시장/PG 골격 + 제작 흐름의 확정분이다. 취소·환불 상태기계, 금액/통화 표현 상세, 세금·관세 산정, 이벤트 원장, PII 처리, 동시성 중재 상세, 스냅샷 상세 명세 등은 **전부 논의 문서**에 있고 확정에 넣지 않았다.
- "확정"의 근거는 사용자 발화와 논리적 귀결이며 스키마·코드·PG 계약·법률로 검증된 것이 아니다. MFG-1의 PAID-후-생성 판단은 단일 DB·자체 제작·같은 앱 관리 전제 위에서만 유효하며, 제작이 외부 시스템으로 나가면 결론이 바뀐다(만료조건 기재).
- 외부 사실(미국 관세, 일본 3DS·PG 스펙)은 2026-07 검색 시점 기준이며 계약·구현 단계 재확인 대상. 두 PG의 실제 API 품질은 검증하지 않았다.
- 이 사업 특유의 축(제작 파트너 정산, B2B 판매 등)이 있다면 이 문서 범위에 잡히지 않았다.
- **v4 추가분의 근거 한계:** ARCH-1의 엔진 비교는 학습 지식 기준이며 벤치마크·실측이 아니다. ARCH-0 만료조건의 N 규칙(일정 1/3·절대 2개월)과 선행 지표 시점(일정 1/4)은 검증된 수치가 아닌 휴리스틱이다. 두 레코드의 괄호 값은 목표 출시일·팀 정보 수신 시 치환한다. 호스팅·관리형 DB 벤더 비교와 언어·프레임워크 선택은 다루지 않았다. GOAL-0(속도 vs 정확성 우선순위 레코드)은 여전히 부재하며, N의 교환비 주인은 사용자다(논의 §0 신규 항목 참조).
- **v5 추가분의 근거 한계:** 외부 사실 중 검색 재검증된 것은 미국 관세(2026-07-05)뿐이고, PayPal eCheck 동작·주 판매세 임계·재수입면세·미국 주법 환불 고지·일본 총액표시·국외이전은 학습 지식(2026년 초) 기반이라 전부 확인 플래그가 문안에 있다. ARCH-2의 정찰 근거는 두 독립 보고의 교차 일치이며 리포 실물 미대조.
