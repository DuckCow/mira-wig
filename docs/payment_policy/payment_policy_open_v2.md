## 1. 스키마 동결 전 반드시 닫아야 하는 결정 (최우선)

### 1.1 세션 스냅샷 명세 확정 `[권고: 아래 명세]`

**전제 점검.** "스냅샷 = 금액을 얼린다"가 깔고 있는 전제는 "얼려야 할 것은 총액"이다. 이 전제를 풀면 — 부분환불·세무·분쟁 증빙·웹훅 경로 성립까지 고려하면 얼려야 할 것은 총액이 아니라 **주문을 브라우저 없이 재구성할 수 있는 전 입력**이다. 그래서 명세가 아래처럼 넓어진다.

| 스냅샷 항목 | 넣는 이유 | 확정 상태 |
|---|---|---|
| 품목·수량·단가 | 기본 | A3(a)로 존재 확정, 항목 세부는 미확정 |
| **라인별 할인·쿠폰 배분액** | 부분환불 산식은 라인별 배분이 있어야 정의됨 | 미확정 `[권고]` |
| **라인별 세액** | 부분환불·세무 | 미확정 `[권고]` |
| 배송비(배송그룹별 분해) | 일부 취소 시 배송비 환불 기준 + 혼합 주문의 그룹 배송 | 미확정 `[권고]` |
| 통화 + 적용 환율 | 표시통화 ≠ 정산통화 시 검증·환불 기준 (글로벌 확정이므로 필수) | 미확정 `[권고]` |
| **배송지·배송방법·수령인 (값 복사)** | 웹훅 경로가 브라우저 없이 주문 생성 + 배송지가 배송비/세액을 결정 | 미확정 `[강한 권고]` |
| 구매자 식별자(게스트면 이메일) | 웹훅 경로에서 주인 없는 주문 방지 | 미확정 `[권고]` |
| **라인별 restockable / 철회배제 동의** | §6 축 R | 미확정, 법률 종속 |

- **배송지 값 복사 vs 참조**: 참조는 결제 개시~웹훅 사이 수정·삭제 가능 → 금액 무결성 깨짐. 반드시 값 복사(또는 불변 버전 참조). `[강한 권고]`
- **되돌리기 난도**: 높음(스키마 핵심). 그래서 최우선.

### 1.2 확정 A2 문구 조정 `[권고]`

A2의 "배송/이행 필드는 결제 후 슬림 Order로"를 **"이행 *상태*(운송장·배송진행·제작진행)는 Order로, 이행 *입력*(배송지·배송방법·수령인)은 세션 스냅샷으로"** 로 분리. 근거: 웹훅 경로는 브라우저 없이 주문을 만들므로 주문 생성의 전 입력이 세션에 있어야 성립(거의 강제된 수정). 배제 대안(입력도 Order에만): 웹훅 경로에서 입력 부재로 주문 생성 불가.

## 2. §3 안전장치 (A3) 세부 강화 — 존재는 확정, 강화는 미확정

### 2.1 (a) 스냅샷 → §1.1로 이관.

### 2.2 (b) 멱등 강화 `[권고]`
- 유니크 제약을 `(provider, paymentKey)` **복합**으로 — 멀티 PG 시 paymentKey가 PG 간 충돌 가능.
- `orders.session_id` 유니크를 **추가로** 병행(택일 아님). paymentKey 유니크는 "같은 결제→두 주문"만, session_id 유니크는 "재시도로 결제키 2개→한 세션 두 주문"을 막음. (A3(b) 원문 "paymentKey/세션 id 유니크"가 이미 둘 다를 함의한다고 읽힘 — 여기서는 "둘 다 필수·택일 아님"의 명확화.)
- 중복 진입은 에러가 아니라 **멱등 성공**(기존 주문 반환). 근거: 클라이언트 재시도가 사용자에게 실패로 보이면 안 됨.

### 2.3 (c) 트랜잭션 경계 `[권고]`
- **PG confirm 호출(외부 HTTP)은 DB 트랜잭션 밖.** 순서: confirm → 트랜잭션(Payment·Order·재고) → 커밋.
- 이로 생기는 "PG 승인 성공 → DB 실패" 창의 복구: 웹훅이 같은 멱등 경로 재진입 → 못 잡으면 대사.
- **confirm 타임아웃 = 불확정**: 실패로 추정 금지, PG 조회 API로 상태 확정 후 분기. 그 사이 "결제 확인 중" 화면 필요(§7.4).
- **부수효과(메일·물류·제작 트리거·분석)는 트랜잭션에 넣지 않고 outbox 행으로 기록 → 워커 발행.** 메일 장애가 결제를 실패시키는 결합 제거.

### 2.4 (d) 대사 확장 `[권고]`
- 양방향: 결제 있음·주문 없음 → 멱등 경로 자동 복구 / 주문 있음·결제 없음·취소됨 → 알람(자동 삭제 금지) / 금액 불일치 → 알람.
- 점검 항목에 "결제 있음 + 주문 없음 + 취소 미완" 추가(망취소 실패 탐지).
- **정산(수수료·입금액) 대사를 별도 층**으로 — 글로벌 PG는 수수료·환율 차감 구조가 달라 회계가 여기서 틀어짐. (토스도 '거래 대사'와 '정산 대사'를 문서상 구분함.)
- 멀티 PG 시 PG별 분리 실행. 출시 첫날부터 가동(초기 트래픽에서 결제 버그 최다).

## 3. 상위 불변식 (정책들의 상위 원칙) `[권고]`

개별 메커니즘 위에 두는 원칙. 아래가 지켜지면 개별 구현은 교체 가능.

1. **확정된 결제는 반드시 주문 생성 또는 환불(망취소) 중 정확히 하나로 귀결되며 절대 무시되지 않는다.** (2.2~2.4 + 망취소 보상 큐를 묶는 최상위 문장. 대사가 이 불변식의 검사기.)
2. **결제 1건·세션 1건당 주문 최대 1개** (§2.2의 두 유니크).
3. **금액의 진실은 서버 스냅샷.** confirm 시 PG 승인 금액 == 스냅샷 금액 서버 검증, 불일치 시 망취소. 클라이언트 금액 절대 불신뢰. (토스 문서도 인증 결과 금액과 사전 저장 금액 대조를 권고 — 클라이언트 금액 조작 방지.)
4. **confirm 경로는 살아있는 카트·현재 가격을 재조회하지 않는다.** 동결은 결제 개시 시점에 동기적으로 완료.
5. **웹훅 취급 — 재작성됨 (아래 §3-불변식5 참조).**

### 3-불변식5. 웹훅 취급 원칙 (검증 후 재작성) `[권고]`

**이전 문구**("웹훅은 트리거일 뿐 진실은 항상 PG 조회 API, 비용은 조회 1회뿐")를 **강등이 아니라 인증 원칙으로 승격·차등화**한다.

**재작성 문구:** *"부수효과를 일으키는 상태 전이는 인증된 데이터로만 수행한다. 페이로드가 인증되지 않거나 불충분하면 조회 API가 곧 그 인증이다."*

- **검증 근거(공식 문서 확인):**
  - PayPal은 정확한 rate limit 수치를 공개하지 않고 유연 운영하며, 회피책으로 폴링 대신 웹훅을 공식 권고 → "웹훅마다 무조건 동기 조회"를 **영구 절대 불변식**으로 두는 건 과함(재전송 폭풍·스케일에서 위험). 다만 이벤트 비례 호출이라 출시 규모에선 실질 위험은 낮음.
  - 토스: HMAC 웹훅 서명은 일부 이벤트(예: 정산·셀러 변경) 헤더에만 포함되고, 가상계좌·결제상태 웹훅은 승인 응답의 secret 대조로 검증 → **"서명 검증됐으니 재조회 불필요"라는 반론이 토스 결제 웹훅에선 전제부터 불성립**. 토스 스스로 웹훅 데이터 정합성 보장을 위한 별도 작업이 필요하다고 안내.
  - PayPal 로컬 서명 검증은 원문 바이트 처리에 민감해 취약하고, 대안(서명 검증 API)은 그 자체가 추가 지연·API 의존을 갖는 호출 → PayPal에선 "서명이니 조회 생략"의 절감이 거의 없음.
- **차등 축(‘중요도’라는 모호한 기준을 대체):** ① 페이로드가 인증되는가, ② 부수효과 있는 상태 전이를 일으키는가, ③ 페이로드가 처리에 충분한가. 셋을 보고 재조회 여부 결정.
- **부속 규칙:** 조회 실패 시 비-2xx 응답 → PG 재전송에 위임(토스 최대 7회, PayPal 약 3일·25회). 최종 방어선은 대사. **토스는 웹훅 수신 후 10초 내 2xx를 요구** → 조회 호출+잠금 대기를 포함한 핸들러 처리 시간이 이 창을 넘지 않도록 운영 파라미터로 관리.
- `[확인 필요: PG별 조회 rate limit·서명 제공 범위 — Stripe/Adyen/엑심베이 등 다른 후보 PG는 미검증]`

## 4. ManufacturingRequest(A4) 세부 `[권고]`

**전제 점검.** "제작은 PAID 후"가 깔고 있는 전제는 "PAID = 제작 착수 신호"다. 이 전제를 풀면 PAID와 제작 착수 사이에 **정책적으로 유용한 간격**이 있음이 드러난다(취소 유예·리스크 검토).

1. **착수 시점 = 취소 정책 분기점(point of no return).** PAID~착수 사이 유예창(무료 취소 가능)과 착수 후 취소 규칙 정의, 착수 이벤트 기록. §7.1 환불 상태기계와 연동.
2. **철회 배제 동의**(주문제작): 체크아웃 시 명시 고지+동의가 있어야 유효한 것으로 파악 → §1.1 스냅샷에 캡처. `[확인 필요: 법률]`
3. **리스크 게이트**: 커스텀 제작품은 차지백 시 재판매 불가 = 전손 → 고위험 주문(고액·해외카드·배송지 불일치 등)은 PAID~착수 사이 수동 검토 홀드. **홀드는 라인이 아니라 주문 전체 이행 대상**(사기 의심 시 재고형 출고도 손실). 단 재판매 가능한(restockable) 라인은 게이트 강도 하향 가능 → §6.
4. **트리거는 outbox 이벤트로.** PAID 트랜잭션 안에서 제작 시스템 직접 호출 금지(§2.3 결합 회귀 방지).
5. **자원 검사 대상은 SKU 유형별로 분기** → §5.2로 통합.

## 5. 혼합 장바구니 아키텍처 (요구사항 B3의 구현)

**전제 점검.** "혼합을 어떻게 처리하나"가 한 층위처럼 보이지만 실제로는 두 층위 — 카탈로그 혼합(확정)과 **주문 혼합(한 주문에 두 유형 라인 공존 여부)**. 설계를 가르는 건 후자.

### 5.1 옵션 전개

- **A. 단일 주문 + 라인 유형 분기 `[권고]`.** 한 세션→한 결제→라인에 유형이 붙은 주문 하나. 채택 근거: ① 확정 멱등 코어(세션↔주문 1:1, session_id 유니크)를 그대로 보존하는 유일한 안. ② 이미 권고한 라인별 배분 스냅샷이 라인 단위 운영 비용을 선지불. ③ 단일 결제 UX. 비용: 이행 상태기계가 주문→라인/배송그룹 수준으로 내려감(B·C에서도 형태만 바꿔 존재).
- **B. 혼합 장바구니 금지(유형별 별도 결제) — 배제.** 요구사항 B3에 정면 위배. 복잡도가 사라지지 않고 결제 2회·배송비 이중화·동시 세션 문제로 변형.
- **C. 한 결제 → 유형별 주문 분할(주문 그룹) — 지금 배제, 조건 기록.** 마켓플레이스형 표준이나 Payment:Order 1:1과 session_id 유니크를 깨고, 한 paymentKey에 N주문의 부분취소 매핑·대사 불변식 재작성 수반. **복수 판매자/마켓플레이스 전환 시 재부상**(만료조건 §9).

### 5.2 A 채택 시 활성화되는 하위 결정 `[권고]`

- **완료 트랜잭션의 자원 검사가 라인 유형별로 분기.** 재고형 = `stock >= n`. MTO 라인 = 아래 셋 중:
  - (a) **무검사 + 리드타임 표기** `[출시 기본 권고]` — 캐파가 탄력적이면 최단순.
  - (b) 기간별 제작 슬롯 조건부 차감 — 캐파가 경성 상한이면 필요. 재고와 같은 의미론이라 잠금 순서가 "세션 → 재고 행 → 슬롯 행, 각 ID 정렬"로 자연 확장.
  - (c) 자재 BOM 차감 — 정확하나 무거워 배제.
  - → P5의 "끌 수 있는 레이어" 철학대로 (a)로 출시, (b) 활성 지표(리드타임 위반율·백로그)를 지금 정의.
- **all-or-nothing 망취소는 두 유형에 걸쳐 하나로**(재고는 됐는데 슬롯 실패 시 전체 망취소).
- 이행 상태기계를 라인/배송그룹 수준으로; **분리 배송 기본**(재고형 먼저 출고, MTO는 제작 후) — 합배송으로 재고형을 몇 주 묶는 기본값은 UX상 배제 권고(단 사업 결정 표기).
- 배송비는 체크아웃에서 배송그룹별 산정·동결(§1.1).
- ManufacturingRequest는 MTO 라인 단위 생성으로 A4 문구 스코프 조정.

## 6. 맞춤제작 축 R (재판매 가능성 → 철회 배제) — 미확정

**확정된 것(축 M): 유형 1·2 모두 MTO.** 여기서 미확정인 것은 축 R뿐.

**전제 점검 1.** "옵션을 골랐으니 맞춤 = 철회 배제"라는 전제는 틀릴 수 있다. 법적 판정 기준(제 지식 기준)은 "옵션을 골랐는가"가 아니라 **"결과물을 다른 고객에게 재판매할 수 있는가"** 쪽 — KR 전자상거래법은 "개별 생산 + 회복 불가능한 중대한 피해 + 사전 고지·별도 동의"를, EU 지침은 "소비자 사양/명백히 개인화"를 요구. 유한한 표준 옵션 조합은 반품돼도 재판매 가능성이 있어 배제 주장이 무효화될 수 있음. `[확인 필요: 법률]`

**전제 점검 2.** "재판매 가능성은 이산/연속이라는 *구조*로 결정된다"도 전제. 실체는 **수요 회전**이라 구조는 대리 지표일 뿐 — 이산이어도 눈금 200종이면 대부분 안 팔려 연속과 같고, 연속이어도 반올림 버킷으로 묶으면 풀링이 되살아남.

### 6.1 restockable 판정 방식 옵션

- **P1. 구조 기준 정적(이산=가능/연속=불가) — 배제.** 위 반례(눈금 200종)에서 틀리고 카탈로그 성장 시 재검토 안 일어남.
- **P2. 조합 단위 정적(이산이면 조합마다 플래그) — 조건부.** 이산 + 조합 수 작을 때만.
- **P3. 버킷/정규화 후 판정 `[권고: 연속의 기본]`.** 연속값을 반올림 버킷으로 정규화, 버킷이 표준 카탈로그에 있으면 재판매 가능, 벗어나거나 자유 입력이면 불가. 비용: 버킷 경계·반올림 규칙 정의(어차피 스냅샷 금액 계산에서 필요).
- **P4. 수요 데이터 기반 동적 — 지금 배제, 만료조건.** 콜드스타트에 무력, 규모 전 과잉설계. 재고 회전 데이터가 쌓이면 P3 버킷 경계를 데이터로 조정하는 형태로 재부상(§9).

이 넷은 **지난 논의의 `restockable` 라인 속성을 대체하는 게 아니라 그 값을 채우는 방법.** 라인에 두 속성을 둔다: `production_mode(STOCKED/MTO)`(축 M) + `restockable`(축 R). `restockable` 하나가 셋을 동시 구동 — 철회 배제 여부, 반품 시 재입고, 차지백 손실 등급(§4-3 게이트 강도).

### 6.2 철회 정책 상위 옵션

- **(i) 두 유형 모두 배제 주장 — 배제 권고.** 유형 1 배제가 법적으로 무효일 수 있어 분쟁·행정 리스크만.
- **(ii) 전부 철회 허용(배제 주장 안 함) — 출시 초기 진지 후보.** 가장 안전·단순. 유형 1 비중이 높고 반품 재판매가 되면 비용도 작음. 비용: 진짜 개인화 주문의 반품 손실.
- **(iii) 라인별 동적 판정 `[권고]`.** restockable로 라인별 판정 — 표준값이면 허용, 개인화 파라미터(자유 입력 등) 건드리면 배제+동의 캡처. 이미 채택 구조와 정합, 법무는 판정 규칙표만 채움.

**미해소 질문(§0-1):** 유형 2 스펙트럼이 이산이면 유형 1과 축 R까지 합쳐 단순화(P2/(ii)), 연속이면 P3+(iii)로. **"세부 조절"이 옵션 체계 밖(사진 업로드·자유 텍스트)으로 나가면 항상 개인화**로 판정표에 "항상 불가" 행 추가.

### 7.1 취소·환불 상태기계 `[런칭 블로킹 권고]`

### 7.2 금액 표현 정책 — **코어/확장 분리** `[코어=런칭 블로킹]`

## 8. 조건부 수용 항목

### 8.1 세션 만료 vs 늦은 승인 레이스 `[조건부 수용]`
- **수용:** 만료는 새 결제 *개시*만 막고, PSP 확정 신호는 만료와 무관하게 공유 핸들러로 흘려 완료 시도. (이전 대화의 "만료 후 승인 = 자동 망취소" 결론을 **대체**함 — 두 기록이 반대이므로 여기서 명문화.)
- **근거:** 동기 수단의 만료~늦은 승인 갭은 분 단위 → 스냅샷 존중 완료가 전환율·CS에서 유리. 재고는 같은 조건부 차감 통과라 오버셀 없음.
- **조건 3개(없으면 수용 철회):** ① 외곽 시한(honor window): 동결 후 X시간 내만 완료, 초과분 망취소(무제한 honor는 프로모션 종료·가격 개편과 충돌). ② 상태기계에 EXPIRED→COMPLETED 전이 명시 허용. ③ 아카이브 지연 > honor window(§7.6).

### 8.2 비동기(지연완료) 결제 수단 `[조건부 수용]`
- **지금 채택:** (i) 동기 수단(카드·월렛)만 지원함을 **설계 경계로 명시 선언**. 현행 정책 유지 가능.
- **유보:** 리뷰의 "(ii) AWAITING_PAYMENT 주문이 미래 기본 후보" — **기본값으로 예약하지 않음.** 근거: (iii) 세션 수명 연장은 "이름만 다른 (ii)"가 아니라 "오염이 무해한 테이블에 대기를 두는 안". 가상계좌류는 미입금 이탈률이 높아 (ii)면 대량의 버려진 대기가 막 정화한 Order 공간을 재오염. 재고 예약은 (ii)에서도 동일 필요.

## 9. 동시성 중재 (A6의 세부) `[권고: 하이브리드]`

**전제 점검.** "잠금 vs 유니크 제약" 양자택일은 "한 메커니즘이 중재+유일성을 겸한다"를 전제. 풀면 중재(누가 수행: 성능·코드경로)와 유일성(정확성 불변식)은 다른 문제이고, 유니크 제약은 A3(b)라 어차피 제거 불가 → 실제 선택지는 "제약만으로 중재까지 시키나, 중재용 잠금을 앞에 더 두나". 또 "유니크=낙관=비차단"도 이 사례엔 불성립(MVCC에서 어차피 인덱스·행에서 대기).

- **채택: 세션 행 잠금(`SELECT … FOR UPDATE`) 첫 줄 중재 + 유니크 제약은 최후 방어선.** 근거: ① A3(c)로 PG 호출이 트랜잭션 밖이라 잠금 보유 = ms 단위(이전 결정이 비용 선지불). ② 데드락 위상 깨끗(같은 세션 confirm/웹훅은 같은 행 → 순수 대기열). ③ 패자가 부수효과 코드를 아예 실행하지 않는 유일한 방식.
- **배제: 유니크 제약 단독 중재.** 블로킹 이점 허상, 패자 경로가 예외 기반 제어흐름, A5 재고 차감 때문에 패자가 재고 행 경합까지 일으키고 롤백으로 버림.
- **배제: 어드바이저리 락(스키마에 안 보임)/Redis 락(DB 커밋과 비원자적 2번째 인프라)/큐 직렬화(=완전 비동기화 재도입).**
- **함께 확정할 규칙:** 잠금 순서 세션 행 → 재고 행 → (MTO면) 슬롯 행, 각 ID 정렬. 획득 후 첫 동작 = 상태 재검사(COMPLETED→기존 주문 멱등 반환, EXPIRED→§8.1 분기). **잠금 있는데 유니크 위반 발생 = 정상 경합 아니라 "잠금 안 탄 경로 존재" 버그 신호** → 사용자엔 멱등 성공, 내부 알람.
- **만료 조건:** 예약 레이어 활성으로 재고 차감이 트랜잭션 밖으로 나가면 제약 단독 중재 재비교 가치 발생 / 주문·결제 서비스 분리 시 행 잠금 불성립 → outbox·saga.
- `[확인 필요: DB 엔진 — Postgres/InnoDB급 잠금 의미론 전제, 실제 엔진 미확인]`

## 13. 확인 필요 플래그 (외부 검증 없이 확정 불가)

- **법률:** 철회 배제 고지·동의 요건(KR 전자상거래법·EU 지침), 표준 옵션 조합의 배제 인정 여부, 거래기록 보존 범위(실패 시도 포함?), 통신판매업·구매안전서비스. → 본 문서는 방향 제시일 뿐 충족 판단 아님.
- **PG 계약:** confirm 중복 응답, 웹훅 재전송·서명 제공 범위(PG별 상이 — 토스는 이벤트별 서명 유무 다름 확인됨), 조회 rate limit, 망취소 시한. Stripe/Adyen/엑심베이 미검증.
- **DB 엔진:** 유니크 인덱스 대기/위반 의미론, InnoDB 중복키 데드락 패턴.
- **도메인 실측:** 제작 슬롯 구조·리드타임(§4·§5.2), 시장별 미입금율(§8.2), 스펙 수요 분포(§6.1 버킷 경계).
- **미결 상류:** MoR/계약 주체(§7.3) — 다수 하류가 종속.

## 15. 이 문서의 검토 경계

대화 기록 + 이번에 검증한 PayPal·토스 공식 문서(§3-불변식5)만을 근거로 함. 실제 스키마·코드·타 PG·법률 요건은 미검증. PayPal rate limit은 수치 비공개라 정량 판단 원리적 불가, 토스 문서도 접속 시점 기준이라 계약 시 재확인 필요. 축 R의 법 서술과 도서산간 배송비 등은 지식 기준 방향 제시. 혼합·맞춤제작 도메인 파라미터(슬롯·리드타임·수요 분포)는 미확인이라 §5.2(b)·§6.1은 그 값 없이 임계를 못 정함.
