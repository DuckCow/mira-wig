## 1. 스키마 동결 전 반드시 닫아야 하는 결정 (최우선)

### 1.1 세션 스냅샷 명세 확정 `[권고: 아래 명세]`
- **상태:** 미확정 (스키마 핵심, 되돌리기 최고난도 → 최우선)
- **전제 점검:** "스냅샷 = 금액을 얼린다"의 전제는 "얼릴 것은 총액". 풀면 — 부분환불·세무·분쟁증빙·웹훅 경로까지 고려 시 얼릴 것은 총액이 아니라 **주문을 브라우저 없이 재구성할 전 입력**. 그래서 명세가 넓어진다.
- **명세(권고):**

| 스냅샷 항목 | 넣는 이유 | 상태 |
|---|---|---|
| 품목·수량·단가 | 기본 | CORE-3(a)로 존재 확정, 세부 미확정 |
| 라인별 할인·쿠폰 배분액 | 부분환불 산식은 라인별 배분 필요 | 미확정 `[권고]` |
| 라인별 세액 | 부분환불·세무 | 미확정 `[권고]` |
| 배송비(배송그룹별 분해) | 일부 취소 시 환불 기준 + 혼합 주문 그룹 배송 | 미확정 `[권고]` |
| 통화 + 적용 환율 | 표시통화 ≠ 정산통화 검증·환불 기준(글로벌 필수) | 미확정 `[권고]` |
| 배송지·배송방법·수령인(값 복사) | 웹훅 경로가 브라우저 없이 주문 생성 + 배송지가 배송비/세액 결정 | 미확정 `[강한 권고]` |
| 구매자 식별자(게스트면 이메일) | 웹훅 경로 주인 없는 주문 방지 | 미확정 `[권고]` |
| **동의한 약관 버전** | 분쟁 증빙(철회배제 동의 옆) | 미확정 `[권고, 신규 G6]` |
| 라인별 restockable / 철회배제 동의 | §6 축 R | 미확정, 법률 종속 |

- **배송지 값 복사 vs 참조:** 참조는 개시~웹훅 사이 수정·삭제 가능 → 금액 무결성 붕괴. 반드시 값 복사(또는 불변 버전 참조). **(v4 승격)** "웹훅 단독 생성의 전 입력이 세션에 있어야 한다"는 원칙과 배송지·수령인 값 복사는 CORE-2 개정 확정으로 **원칙 확정** — 본 절에 남는 미확정은 스냅샷 명세의 필드 상세다.
- **진행 전략(v4, ARCH-1의 귀결 권고):** 확정분 필드는 컬럼으로, 미확정분은 JSONB로 시작 — 스키마 동결 게이트(§1.1+§1.3 후)를 지키면서 Track 1 골격을 진행하는 배치.
- **파급(신규):** PII 값 복사가 §7.5 원장·삭제권과 충돌 → 아래 1.3(PII 볼트)과 동일 층에서 함께 결정.
- **근거 출처:** ④(전제 점검·명세 확장)

### 1.2 (v4 이관 종료) 확정 CORE-2 문구 조정
- **상태:** 승인·확정 이관 완료 — 개정 문구("이행 상태는 Order / 이행 입력은 세션 스냅샷")와 파생 규칙(스냅샷 불변 유지 + Order 오버라이드 필드·변경 이력 + 과세구역 이탈 등 금액이 바뀌는 변경 불허)은 확정 문서 **CORE-2(v4)** 참조. 여기 남는 것 없음. 오버라이드 필드 자리는 Track 1 A2 스키마 요건으로 전달됨.

### 1.3 PII 볼트 분리 vs 불변 스냅샷·원장 `[권고: (a) 볼트]` — 신규(구 G1, §1으로 승격)
- **상태:** 미확정 (스키마·법, 되돌리기 매우 비쌈 → 최우선)
- **전제 점검:** §1.1은 배송지·수령인·이메일 **값 복사**를, §7.5는 **원본 페이로드 append-only 원장**을 둔다. 글로벌(특히 캘리포니아 CPRA 삭제권·일본 APPI, 향후 EU GDPR)에서 삭제권과 정면 충돌. 거래기록은 법적 보존으로 삭제 거부 가능하나, 원문 페이로드 로그 전체까지 그 근거가 커버되는지는 관할별 불확실.
- **옵션:**
  - **(a) PII 볼트 분리 + 스냅샷/원장엔 토큰 참조, 삭제 = 볼트 crypto-shredding — 권고.** 스키마 초기 삽입은 싸고 나중은 전 테이블 마이그레이션. §1.1 "값 복사"와 양립(볼트 레코드가 불변 버전).
  - (b) 법적 보존 근거로 원문 보존 + 삭제 요청 시 근거 회신 — 법률 종속, 페이로드 로그 방어 여부 미확인. `[확인 필요: 법률]`
  - (c) 사후 마스킹 배치 — 배제: §7.5 append-only와 충돌.
- **근거 출처:** ④ + SCOPE-2(관할 활성)로부터의 귀결
- **의존·파급:** §1.1·§7.5와 동일 스키마 층. **(v4)** CORE-2 개정 확정으로 세션 스냅샷의 PII(배송지·수령인) 포함이 확정됨 → 본 결정의 압력·시급성 증가(확정 문서 CORE-2가 이를 "인지된 채 승인"으로 명기). `[확인 필요: 법률 — 관할별 삭제권 vs 거래기록 보존 범위]`

## 2. CORE-3 안전장치 세부 강화 — 존재는 확정, 강화는 미확정

### 2.2 (b) 멱등 강화 `[권고]`
- 유니크 제약을 `(provider, paymentKey)` **복합**으로 — 멀티 PG(PG-1 확정)에서 paymentKey가 PG 간 충돌 가능. **멀티 PG day-one이라 이제 출시 요건.**
- `orders.session_id` 유니크를 **추가로** 병행(택일 아님). paymentKey 유니크는 "같은 결제→두 주문"만, session_id 유니크는 "재시도로 결제키 2개→한 세션 두 주문"을 막음.
- 중복 진입은 에러가 아니라 **멱등 성공**(기존 주문 반환).

### 2.3 (c) 트랜잭션 경계 `[권고]`
- **PG confirm(외부 HTTP)은 DB 트랜잭션 밖.** 순서: confirm → 트랜잭션(Payment·Order·재고·MR) → 커밋. (MR insert는 MFG-1로 트랜잭션 안 확정.)
- "PG 승인 성공 → DB 실패" 창 복구: 웹훅이 같은 멱등 경로 재진입 → 못 잡으면 대사.
- **confirm 타임아웃 = 불확정:** 실패 추정 금지, PG 조회 API로 상태 확정 후 분기. 그 사이 "결제 확인 중" 화면(§7.4).
- **부수효과(메일·물류·제작 트리거·분석·상태알림)는 트랜잭션에 넣지 않고 outbox 행 → 워커 발행.** (MFG-2 상태 알림도 여기.) **(v4)** 워커 폴링은 `FOR UPDATE SKIP LOCKED` 표준 패턴 — ARCH-1 채택 근거 ⑶.
- **신규(G6):** outbox 소비자는 at-least-once 발행이므로 **멱등 처리** 원칙 명시.

### 2.4 (d) 대사 확장 `[권고]`
- 양방향: 결제 있음·주문 없음 → 멱등 경로 자동 복구 / 주문 있음·결제 없음·취소됨 → 알람(자동 삭제 금지) / 금액 불일치 → 알람.
- "결제 있음 + 주문 없음 + 취소 미완"(망취소 실패 탐지) 추가.
- **정산(수수료·입금액) 대사를 별도 층** — 글로벌 PG는 수수료·환율 차감 구조가 달라 회계가 여기서 틀어짐. PG별 분리 실행(멀티 PG 확정으로 필수). 출시 첫날부터 가동.

## 3. 상위 불변식 `[권고]`

1. **확정된 결제는 반드시 주문 생성 또는 환불(망취소) 중 정확히 하나로 귀결되며 절대 무시되지 않는다.** (대사가 이 불변식의 검사기.)
2. **결제 1건·세션 1건당 주문 최대 1개** (§2.2 두 유니크).
3. **금액의 진실은 서버 스냅샷.** confirm 시 PG 승인 금액 == 스냅샷 금액 서버 검증, 불일치 시 망취소. 클라이언트 금액 절대 불신뢰.
4. **confirm 경로는 살아있는 카트·현재 가격을 재조회하지 않는다.** 동결은 결제 개시 시점에 동기 완료.
5. **웹훅 취급 (아래 §3-불변식5).**

### 3-불변식5. 웹훅 취급 원칙 `[권고]`
- **재작성 문구:** *"부수효과를 일으키는 상태 전이는 인증된 데이터로만 수행한다. 페이로드가 인증되지 않거나 불충분하면 조회 API가 곧 그 인증이다."*
- **검증 근거(외부, 접속 시점 기준):** PayPal은 rate limit 수치 비공개·웹훅 권고 → "웹훅마다 무조건 동기 조회"를 영구 절대 불변식으로 두는 건 과함. 토스는 HMAC 서명이 이벤트별로 다르게 제공 → "서명됐으니 재조회 불필요"가 결제 웹훅에선 전제부터 불성립. → **차등 축:** ①페이로드 인증 여부 ②부수효과 상태 전이 여부 ③처리 충분성.
- **부속 규칙:** 조회 실패 시 비-2xx → PG 재전송 위임. 최종 방어선은 대사. 핸들러 처리 시간이 PG 요구 응답창(예: 토스 수초 내 2xx)을 넘지 않도록 운영 파라미터 관리.

## 4. ManufacturingRequest 세부 `[권고]` (MFG-1·MFG-2로 상당 부분 확정 이관)

> MR 생성 시점(PAID 트랜잭션 내)·상태 기록 구조는 MFG-1·MFG-2로 확정. 여기 남는 것은 착수 정책·게이트 등 미확정분.

1. **착수 시점 = 취소 정책 분기점(point of no return).** PAID~착수 사이 유예창(무료 취소)과 착수 후 취소 규칙 정의, 착수 이벤트는 MFG-2 전이 이력에 기록. §7.1 환불 상태기계와 연동.
2. **철회 배제 동의**(주문제작): 체크아웃 시 명시 고지+동의 → §1.1 스냅샷 캡처. `[확인 필요: 법률]`
3. **리스크 게이트:** 커스텀 제작품은 차지백 시 재판매 불가 = 전손 → 고위험 주문(고액·해외카드·배송지 불일치)은 PAID~착수 사이 수동 검토 홀드. **홀드는 라인이 아니라 주문 전체 이행 대상.** restockable 라인은 게이트 강도 하향 가능 → §6.
4. **트리거는 outbox 이벤트로.** PAID 트랜잭션 안에서 제작 시스템 직접 호출 금지(§2.3). (MFG-1과 정합: 트랜잭션 안은 MR *행 생성*까지, 공장 통지는 outbox.)

## 5. 혼합 장바구니 아키텍처 (SCOPE-4 구현)

- **전제 점검:** "혼합 처리"는 두 층위 — 카탈로그 혼합(확정)과 **주문 혼합(한 주문에 두 유형 라인 공존 여부)**. 설계를 가르는 건 후자.

### 5.1 옵션 전개
- **A. 단일 주문 + 라인 유형 분기 `[권고]`.** 한 세션→한 결제→라인에 유형이 붙은 주문 하나. ① 확정 멱등 코어(세션↔주문 1:1, session_id 유니크) 보존하는 유일 안. ② 라인별 배분 스냅샷이 라인 단위 운영 비용 선지불. ③ 단일 결제 UX. 비용: 이행 상태기계가 라인/배송그룹 수준(MFG-2와 정합).
- **B. 혼합 금지(유형별 별도 결제) — 배제.** SCOPE-4 위배.
- **C. 한 결제 → 유형별 주문 분할 — 지금 배제, 조건 기록.** Payment:Order 1:1·session_id 유니크 파괴. **복수 판매자/마켓플레이스 전환 시 재부상**(§9 만료조건).

### 5.2 A 채택 시 하위 결정 `[권고]`
- **완료 트랜잭션 자원 검사가 라인 유형별 분기.** 재고형 = `stock >= n`(CORE-5). MTO 라인 = 아래 중:
  - (a) **무검사 + 리드타임 표기** `[출시 기본 권고]` — 캐파 탄력적이면 최단순.
  - (b) 기간별 제작 슬롯 조건부 차감 — 캐파가 경성 상한이면. 잠금 순서 "세션 → 재고 행 → 슬롯 행, 각 ID 정렬"로 확장. 활성 지표(리드타임 위반율·백로그)는 MFG-2 전이 이력에서 산출.
  - (c) 자재 BOM 차감 — 배제(무거움).
  - → (a)로 출시, (b) 활성 지표 지금 정의.
- **all-or-nothing 망취소는 두 유형에 걸쳐 하나로.**
- 이행 상태기계를 라인/배송그룹 수준; **분리 배송 기본**(재고형 먼저, MTO는 제작 후). 합배송으로 재고형을 몇 주 묶는 기본값은 배제 권고(사업 결정 표기).
- 배송비는 체크아웃에서 배송그룹별 산정·동결(§1.1).
- MR은 MTO 라인 단위 생성(MFG-1과 정합).

## 6. 맞춤제작 축 R (재판매 가능성 → 철회 배제) — 미확정

**확정(축 M): 유형 1·2 모두 MTO(MFG-M).** 미확정은 축 R.

- **전제 점검 1:** "옵션 골랐으니 맞춤 = 철회 배제"는 틀릴 수 있다. 법적 기준은 "옵션을 골랐는가"가 아니라 **"결과물을 다른 고객에게 재판매할 수 있는가"**. 유한 표준 옵션 조합은 반품돼도 재판매 가능성이 있어 배제 주장이 무효화될 수 있음.
- **전제 점검 2:** "재판매 가능성은 이산/연속 구조로 결정"도 전제. 실체는 **수요 회전** — 이산이어도 눈금 200종이면 대부분 안 팔려 연속과 같고, 연속이어도 반올림 버킷으로 묶으면 풀링 회복.

### 6.0 관할 차원 (신규 G2)
- SCOPE-2로 철회권이 관할별 상이: **KR(청약철회 7일 + "개별생산+회복불가+사전고지·별도동의" 배제요건), US(연방 철회권 없음, 대신 FTC 통신판매 배송기한 규칙 → MTO 리드타임 표시·지연 시 환불 의무와 직결), JP(법정 쿨링오프 없음, 반품특약 미표시 시 8일 반품 적용).** EU는 1차 시장 아님 → 만료조건(EU 진출 시 14일 철회권·SCA 활성).
- **판정표를 (라인 속성 × 배송지 관할) 2차원으로.** §7.1에 관할별 법정 환불 시한 항목 추가. `[확인 필요: 법률]`

### 6.1 restockable 판정 방식 옵션
- **P1. 구조 정적(이산=가능/연속=불가) — 배제.** 반례(눈금 200종)에서 틀림.
- **P2. 조합 단위 정적 — 조건부.** 이산 + 조합 수 작을 때만.
- **P3. 버킷/정규화 후 판정 `[권고: 연속의 기본]`.** 연속값을 반올림 버킷 정규화, 표준 카탈로그에 있으면 재판매 가능. 비용: 버킷 경계·반올림 규칙 정의(스냅샷 금액 계산에서 어차피 필요).
- **P4. 수요 데이터 기반 동적 — 지금 배제, 만료조건.** 콜드스타트 무력. 회전 데이터 축적 시 P3 경계를 데이터로 조정(§12).
- 라인에 두 속성: `production_mode(STOCKED/MTO)`(축 M) + `restockable`(축 R). restockable 하나가 셋 구동 — 철회 배제·반품 재입고·차지백 손실 등급(§4-3).

### 6.2 철회 정책 상위 옵션
- **(i) 모든 유형 배제 주장 — 배제 권고.** 유형 1 배제가 무효일 수 있어 리스크만.
- **(ii) 전부 허용 — 출시 초기 진지 후보.** 가장 안전·단순. SCOPE-2가 EU 없는 구성이라(연방 철회권 없는 US 포함) 축 R 법적 압력이 상대적으로 낮아 이 옵션의 비용이 작음.
- **(iii) 라인별 동적 판정 `[권고]`.** restockable로 라인별 — 표준값이면 허용, 개인화 파라미터 건드리면 배제+동의 캡처. 이미 채택 구조와 정합, 법무는 (관할 × 규칙) 판정표만 채움.
- **미해소(§0-2):** 유형 2 이산이면 P2/(ii)로 단순화, 연속이면 P3+(iii). "세부 조절"이 옵션 체계 밖(사진 업로드·자유 텍스트)이면 항상 개인화 → 판정표 "항상 불가" 행.

## 8. 조건부 수용 항목

### 8.1 세션 만료 vs 늦은 승인 레이스 `[조건부 수용]`
- **수용:** 만료는 새 결제 *개시*만 막고, PSP 확정 신호는 만료와 무관하게 공유 핸들러로 흘려 완료 시도.
- **근거:** 동기 수단의 만료~늦은 승인 갭은 분 단위 → 스냅샷 존중 완료가 전환율·CS 유리. 재고/슬롯은 같은 조건부 차감 통과라 오버셀 없음.
- **조건 3개(없으면 철회):** ① 외곽 시한(honor window): 동결 후 X시간 내만 완료, 초과분 망취소. ② 상태기계 EXPIRED→COMPLETED 전이 명시 허용. ③ 아카이브 지연 > honor window(§7.6).

### 8.2 비동기(지연완료) 결제 수단 `[조건부 수용 — §0-1로 재개봉]`
- **지금 채택:** (i) 동기 수단(카드·월렛)만 지원함을 **설계 경계로 명시 선언**.
- **숨은 전제(신규 명시):** 이 경계는 SCOPE-2와 결합 시 **"카드·월렛으로 전환율이 성립하는 시장·수단만 출시한다"**는 선택을 암묵 내포. **특히 일본 편의점 결제가 이 경계에 걸린다(§0-1).** 편의점을 넣으려면 경계를 풀어야 하고 §12 연쇄 발동.
- **유보:** "(ii) AWAITING_PAYMENT 주문이 미래 기본 후보" — 기본값 예약 안 함. 가상계좌·편의점류는 미입금 이탈률이 높아 (ii)면 버려진 대기가 Order 공간 재오염.
- **그 시점 결정 기준 2개:** ① 다운스트림(ERP·CS)이 '입금대기 주문' 개체를 요구하는가 → 요구하면 (ii). ② 세션 orderId가 고객 안내 아티팩트로 충분한가 → 충분하면 세션 수명 연장(iii). `[확인 필요: 대상 시장별 미입금율 실측 — 특히 일본 편의점]`

### 8.3 두 탭 이중 결제 `[수용, 단 자동환불 범위 축소 — 신규 교정]`
- **이전:** 사후 탐지(동일 사용자·구성·근접 시각 → CS/자동환불).
- **교정:** "동일 구성·근접 시각"은 휴리스틱이라 오탐 가능(선물 등 정당 중복 존재). session_id 유니크(§2.2)가 같은 세션 중복은 이미 차단 → 두 탭 = 두 세션 = 기술적으로 구분 불가한 별개 주문. **자동환불은 기술적으로 확정적인 경우로 좁히고, 휴리스틱 매치는 플래그 + 고객 확인(또는 단시간 이행 보류)으로 낮춤.**
- **근거:** §8.1 하에서 만료로 이중 결제를 예방하는 건 원리적 불가 → 사후 처리는 귀결이나, 자동 조치의 확정성은 별개 문제.

## 9. 동시성 중재 (CORE-6 세부) `[권고: 하이브리드]`
- **전제 점검:** "잠금 vs 유니크 제약" 양자택일은 "한 메커니즘이 중재+유일성 겸함"을 전제. 풀면 중재(누가 수행)와 유일성(정확성 불변식)은 다른 문제, 유니크는 CORE-3(b)라 제거 불가 → 실제 선택지는 "제약만으로 중재까지 시키나, 중재용 잠금을 앞에 더 두나".
- **채택: 세션 행 잠금(`SELECT … FOR UPDATE`) 첫 줄 중재 + 유니크 제약 최후 방어선.** ① CORE-3(c)로 PG 호출이 트랜잭션 밖이라 잠금 보유 = ms 단위. ② 데드락 위상 깨끗(같은 세션 confirm/웹훅 = 같은 행 → 순수 대기열). ③ 패자가 부수효과 코드를 아예 실행 안 하는 유일 방식.
- **배제:** 유니크 단독 중재 / 어드바이저리 락 / Redis 락(비원자적 2번째 인프라) / 큐 직렬화(=완전 비동기화 재도입).
- **함께 확정할 규칙:** 잠금 순서 세션 행 → 재고 행 → (MTO면) 슬롯 행 → **(MTO면) MR 행**, 각 ID 정렬. 획득 후 첫 동작 = 상태 재검사(COMPLETED→멱등 반환, EXPIRED→§8.1 분기). 잠금 있는데 유니크 위반 = "잠금 안 탄 경로" 버그 신호 → 사용자엔 멱등 성공, 내부 알람.
- **만료조건:** 예약 레이어 활성으로 재고 차감이 트랜잭션 밖으로 나가면 제약 단독 중재 재비교 / 주문·결제 서비스 분리 시 행 잠금 불성립 → outbox·saga.
- **전제 해소(v4):** ARCH-1로 PostgreSQL + READ COMMITTED 확정 — 본 절의 행 잠금(`SELECT … FOR UPDATE`)·유니크 의미론 전제가 성립. 단 본 설계는 READ COMMITTED 전제이므로 **격리 수준 상향은 직렬화 실패 재시도 재설계 없이 금지**(ARCH-1 만료조건 ②, §12 등재).

## 10. 출시 후로 미룸 `[기록: 향후 — 지금은 상태 필드·훅·기준만 예약]`
- **차지백·분쟁:** Dispute 상태, 접수 시 이행 중단 훅(제작·출고), 증빙 패키지(스냅샷·커스터마이징 기록·MFG-2 전이 이력·배송추적). **승격 조건: 주문제작 비중 높으면 §4-3 게이트와 함께 런칭 블로킹 재분류.**
- **부정거래 방어:** 세션 생성 속도 제한, 벨로시티 룰, 3DS 기준. **단 일본은 3DS가 규제 요건이라 §7.3에서 이미 부분 승격.**
- **혼합 결제(적립금/쿠폰+카드):** 소비 시점, 동시 세션 이중 사용 방지, 환불 시 역순 환원.
- **auth/capture 분리:** 지금 배제. Payment 상태 모델에 AUTHORIZED↔CAPTURED 여지 남길지는 지금 결정(글로벌 실물엔 배송 시 매입 시장 존재).
- **다중 PG 라우팅 자동화**(PG-1은 정적 라우팅으로 출시) / **세션 단계 재고 예약 레이어**.
- **PG 전면 장애 대응(신규 G6):** 장애 = 매출 전면 중단 → 폴백 PG 라우팅·사용자 공지 기준. 승격 조건: 단일 PG 의존 구간이 생기면.

## 15. 이 문서의 검토 경계
대화 기록 + 이번에 검증한 외부 자료(미국 de minimis/관세 2026-07 검색, 엑심베이·KG이니시스 PayPay·수단·정산, 일본 3DS·특정상거래법, PayPal·토스 웹훅 원리)만을 근거로 함. 실제 스키마·코드·타 PG·법률·세무·관세 요건은 미검증. 관세 수치는 유동적이라 정량 인용 회피. 두 PG의 실제 API 품질·자사몰 PayPay 가용성은 계약 단계 재확인. 축 R의 법 서술·관할 시한은 지식 기준 방향 제시이지 판단 아님. 혼합·맞춤제작 도메인 파라미터(슬롯·리드타임·수요 분포·미입금율)는 미확인이라 §5.2(b)·§6.1은 그 값 없이 임계를 못 정함. **v4 추가분:** 검색 없이(시점 비민감) 승인된 권고의 반영이며, 엔진 비교는 학습 지식·N 규칙과 1/4 시점은 휴리스틱임을 해당 레코드(ARCH-0·ARCH-1)에 표기함. 2026-07-05 검토의 별도 diff는 미병합 상태로 남아 있음(개정 이력 참조).
