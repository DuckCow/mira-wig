> Status: design lock, not an implementation patch.
> Date: 2026-07-07.

> Scope: future Toss success callback handling, `paymentKey` persistence, and `orderId` strategy.

Official Toss sources checked:

- Toss Payments core API reference: <https://docs.tosspayments.com/reference>

## 1. Purpose

This document locks the future Toss success callback handling and Toss `orderId` strategy for D1-B.

It turns the Toss callback/paymentKey persistence recon into a concrete design decision:

```text
Toss orderId is deterministically derived from Payment.id.
Toss paymentKey is persisted as Payment.providerRef after success callback validation.
Toss confirm uses Payment.providerRef as paymentKey.
Payment.providerPaymentKey is set only after Toss confirm returns DONE.
```

This is a design lock only. It does not implement the callback route, real Toss adapter, provider HTTP calls, or schema changes.

## 2. Non-goals

- No real Toss API calls.
- No Toss adapter implementation.
- No schema change.
- No migration.
- No credential wiring.
- No webhook implementation.
- No void/cancel implementation.
- No settlement, fees, or FX.
- No live enablement.

## 3. Official Toss facts

- Toss success redirect returns payment information through `successUrl` query parameters. The official guide says to verify the returned `amount` against the original requested amount.
- Toss says the server should store `paymentKey`, `orderId`, and `amount` because they are needed for confirm, lookup, and cancel.
- Toss confirm is `POST /v1/payments/confirm`.
- Toss confirm body requires `paymentKey`, `orderId`, and `amount`.
- Toss `paymentKey` is the Toss-side payment identity. It is unique, identifies the payment, persists across status changes, and is used for confirm, lookup, and cancel.
- Toss `orderId` is the merchant-created order number. It is generated by the merchant during payment request and persists across status changes.
- Toss `orderId` must be 6-64 characters and use English letters, numbers, and allowed special characters `-` and `_`.
- Toss API Basic auth uses the secret key server-side. The secret key and Authorization header must never be exposed to the browser, logs, GitHub, or client code.
- Toss idempotency uses the `Idempotency-Key` request header for POST APIs. The key is limited to 300 characters and should be reused for the same operation retry.

## 4. Decision

Decision:

```text
For D1 Toss, orderId is deterministic and derived from Payment.id.
Recommended shape: mira_toss_{payment.id}.
Payment.providerRef stores Toss paymentKey after callback validation.
Payment.providerPaymentKey stores Toss paymentKey only after confirm DONE.
```

No new schema field is needed for Toss `orderId` under this decision.

The locked split is:

```text
Toss orderId = merchant-created local order reference derived from Payment.id.
Toss providerRef = Toss paymentKey after validated success callback.
Toss providerPaymentKey = Toss paymentKey after confirm response proves DONE.
Toss providerConfirmIdempotencyKey = Toss Idempotency-Key.
```

Do not store Toss `orderId` in `Payment.providerRef`. Do not write Toss `paymentKey` to `Payment.providerPaymentKey` before confirm.

## 5. orderId format

Recommended future format:

```text
mira_toss_{payment.id}
```

Requirements satisfied:

- Provider-prefixed: `mira_toss_` scopes the value to the Toss payment flow.
- Deterministic: the same `Payment.id` always yields the same Toss `orderId`.
- Reversible: strip the `mira_toss_` prefix to recover `Payment.id`.
- Toss-compatible: current `Payment.id` values are cuid-style letters/numbers, and the prefix uses only letters and `_`.
- 6-64 chars: the prefix plus current cuid-style `Payment.id` fits the Toss limit.
- Unique per local payment attempt: `Payment.id` is the local payment attempt primary key.
- Stable across retry/refresh: no random suffix is generated outside persisted state.
- Multiple attempts safe: each payment attempt has a distinct `Payment.id`.

Rejected for D1:

- `mira_toss_kr_{payment.id}`: valid but not needed. Market is already available through the local `CheckoutSession`; adding market to the order id increases parsing surface without adding D1 safety.
- Random suffix: rejected unless persisted, because callback recovery must reconstruct the local `Payment.id`.
- Mode suffix: rejected unless provider mode is durably persisted. Current schema does not persist sandbox/live mode on `Payment`.
- `CheckoutSession.id`: rejected because one checkout session can have multiple payment attempts.
- `Payment.idempotencyKey`: rejected because it is an initiate/local attempt key, not a merchant order reference.

Exposing `Payment.id` inside Toss `orderId` is acceptable for D1 because it is not a secret. If opaque order IDs are required later, add a persisted provider order reference field instead of weakening callback recovery.

## 6. Callback route decision

Future route:

```text
GET /api/payments/toss/success
```

This should be a route handler, not a server action, because Toss redirects the buyer's browser to `successUrl`.

Expected query params:

```text
paymentKey
orderId
amount
```

The route handler should stay thin and delegate validation, persistence, and confirm orchestration into `src/lib/payment/**` so payment logic remains under the STRICT payment core path.

## 7. Callback validation order

The future route/core handler must validate in this order:

1. Parse required query params: `paymentKey`, `orderId`, `amount`.
2. Validate `amount` as an integer.
3. Validate `orderId` format and the `mira_toss_` prefix.
4. Recover `Payment.id` from `orderId`.
5. Load local `Payment` with its checkout session.
6. Verify `Payment.provider` is `TOSS`.
7. Verify `Payment.providerPaymentKey` is null unless the payment is already succeeded idempotently.
8. Verify status is pending or already completed in an allowed way.
9. Verify local `Payment.amount` equals callback `amount`.
10. Verify local currency and market are compatible with D1 Toss (`KRW`, KR card route).
11. Verify derived `orderId` from `Payment.id` exactly equals the callback `orderId`.
12. Persist `Payment.providerRef = paymentKey` with compare-and-set semantics.
13. Trigger server-side Toss confirm.

Do not call confirm if any validation fails or if `providerRef` persistence does not succeed.

## 8. providerRef persistence semantics

- Write Toss `paymentKey` to `Payment.providerRef` after callback validation and before confirm.
- Keep `providerRef` after confirm.
- `providerRef` may equal final `providerPaymentKey` after confirm.
- This is acceptable because the timing and meaning differ: `providerRef` is the pre-confirm provider reference, while `providerPaymentKey` is final-only local capture identity.
- A duplicate callback with the same `paymentKey` is idempotent.
- A duplicate callback with a different `paymentKey` must fail closed or move to manual review.
- `providerRef` write failure must stop before confirm.

Persistence must be compare-and-set style:

```text
write when providerRef is null, or accept when providerRef already equals callback paymentKey.
never overwrite a different providerRef.
```

## 9. Confirm interaction

Future Toss confirm mapping:

```text
body.paymentKey = Payment.providerRef
body.orderId = derived orderId from Payment.id
body.amount = Payment.amount
header.Idempotency-Key = Payment.providerConfirmIdempotencyKey
```

Confirm must require `providerRef` for Toss. Missing `providerRef` is a STOP/programmer failure for Toss real-provider flow.

Once callback persistence exists, confirm must not rely on callback `providerPaymentKey?` input as the durable carrier for Toss `paymentKey`. The durable carrier is `Payment.providerRef`; `Payment.providerPaymentKey` remains final-only and is set only after Toss confirm returns `DONE` and amount/currency/order identity checks pass.

## 10. Security / tamper resistance

- Callback query params are untrusted browser-boundary input.
- Server code must not trust `amount`, `orderId`, or `paymentKey` without local validation.
- Deterministic `orderId` binds the callback to one local `Payment`.
- The local server must validate provider, status, amount, currency, market, and exact derived `orderId` before writing `providerRef`.
- Auth/session can be used if present, especially for redirect UX and user ownership checks, but must not be the only correctness boundary. Browser session loss must not make the payment-core binding unsafe.
- A signed state token is not required for D1 if deterministic order binding and server-side confirm are locked.
- Do not log full Toss `paymentKey`, Toss secret key, Basic Authorization header, raw provider payloads, or sensitive payer data.
- Diagnostics should use safe status/code/request id/safe message fields only.

## 11. Failure / retry semantics

- Missing `paymentKey`, `orderId`, or `amount`: reject before DB write and do not confirm.
- Invalid amount: reject before DB write and do not confirm.
- Invalid `orderId` format or prefix: reject before DB write and do not confirm.
- `orderId` not found: reject before DB write and do not confirm.
- Wrong amount: reject before `providerRef` write and do not confirm.
- Wrong provider: reject before `providerRef` write and do not confirm.
- Non-pending payment: allow only reviewed idempotent already-succeeded handling; otherwise fail closed/manual review.
- Already succeeded with same Toss `paymentKey`: treat as idempotent success/status redirect if local identity, amount, and provider match.
- Duplicate callback with same `paymentKey`: reuse existing `providerRef` and continue/retry confirm with the same confirm idempotency key.
- Duplicate callback with different `paymentKey`: never overwrite; fail closed/manual review.
- `providerRef` write failure: retryable local failure, no confirm.
- Confirm retryable failure after `providerRef` write: keep `providerRef`, reuse `providerConfirmIdempotencyKey`, allow refresh/retry.
- Lost browser session: payment-core correctness relies on deterministic order binding plus server confirm; user-facing result recovery may redirect to login or status.

## 12. Future test plan

Required tests for the implementation patch:

- Derived orderId maps to exactly one local `Payment`.
- Invalid orderId fails.
- Wrong amount fails before `providerRef` write.
- Callback persists `paymentKey` as `providerRef`.
- `providerPaymentKey` remains null before confirm `DONE`.
- Duplicate same `paymentKey` is idempotent.
- Duplicate different `paymentKey` fails/manual review.
- Confirm uses `providerRef` as `paymentKey`.

- Confirm requires `providerRef` for Toss.
