## 1. Purpose

This document locks the future Toss confirm adapter design for D1-B.

It defines:

```text
local Payment fields -> Toss confirm request
Toss Payment response -> normalized provider success
Toss error/ambiguous states -> local taxonomy
Toss diagnostics -> safe redacted diagnostics
```

This is a design lock only. It is not:

- a Toss HTTP implementation;
- a live enablement plan;
- a webhook plan;
- a void/refund plan.

## 2. Non-goals

- No real Toss adapter implementation.
- No Toss API calls.
- No credentials.
- No schema change.
- No migration.
- No webhook implementation.
- No void/cancel implementation.
- No settlement, fees, or FX.
- No execution-time cross-PG fallback.
- No live enablement.

## 3. Official Toss facts

- Toss confirm endpoint is `POST /v1/payments/confirm`.
- Toss confirm request requires `paymentKey`, `orderId`, and `amount`.
- A successful confirm returns a Toss `Payment` object.
- Toss `paymentKey` is the Toss-issued payment identity. It identifies the payment, is unique within Toss's documented payment identity scope, persists across status changes, and is used for confirm, lookup, and cancel.
- Toss `orderId` is the merchant-created order identifier. It must be generated by the merchant during payment request, is 6-64 characters, and uses letters, numbers, `-`, and `_`.
- Toss payment window/widget success redirect provides `paymentKey`, `orderId`, and `amount`.
- The server must verify the redirected `amount` against the originally requested amount before confirm.
- Basic auth uses the secret key plus `:` before base64 encoding.
- Toss secret keys must remain server-only.
- `Idempotency-Key` is used for POST idempotency.
- Toss idempotency keys have a max length of 300 characters and are valid for 15 days from first use.
- Toss documents idempotency support for all POST APIs.
- Toss test secret keys begin with `test_sk`; live secret keys begin with `live_sk`.

## 4. Current local fields and invariants

Locked local invariants:

```text
Toss orderId = mira_toss_{Payment.id}
Payment.providerRef = Toss paymentKey after callback validation and before confirm
Payment.providerConfirmIdempotencyKey = outbound Toss Idempotency-Key source
Payment.providerPaymentKey = Toss paymentKey only after Toss confirm returns DONE
Payment.idempotencyKey = initiate/local attempt key, not confirm key
```

Current schema supports this split:

```text
Payment.providerRef String?
Payment.providerConfirmIdempotencyKey String? @unique
Payment.providerPaymentKey String?
@@unique([provider, providerPaymentKey])
@@index([provider, providerRef])
```

The current Toss callback scaffold persists `Payment.providerRef` from the success callback after local validation. It does not call Toss HTTP, does not call `provider.confirm`, and does not complete local payment/order.

## 5. Confirm request mapping

Future request mapping is locked as:

```text
POST /v1/payments/confirm
Authorization: Basic base64(TOSS_SECRET_KEY + ":")
Idempotency-Key: Payment.providerConfirmIdempotencyKey

body.paymentKey = Payment.providerRef
body.orderId = deriveTossOrderId(Payment.id)
body.amount = Payment.amount
```

Rules:

- `paymentKey` must come only from persisted `Payment.providerRef`.
- Missing `providerRef` fails before HTTP.
- `orderId` is re-derived, not persisted.
- `amount` uses the local Payment amount, not callback amount.
- Callback query `amount` is validation evidence only.
- Unchecked client input must not supply confirm body, auth, or idempotency fields.

The confirm adapter must not read `paymentKey`, `orderId`, `amount`, `Idempotency-Key`, secret key, provider, provider mode, or currency from unchecked browser input.

## 6. Pre-HTTP guard conditions

Before any Toss HTTP request, the future adapter or its immediate caller must verify:

- provider is `TOSS`;
- payment is in an allowed pending state;
- `providerRef` exists;
- `providerPaymentKey` is null;
- `providerConfirmIdempotencyKey` exists;
- local currency and market are D1 Toss-compatible: KR/KRW;
- local amount is a valid integer;
- derived orderId is valid and canonical;
- live mode is not enabled unless an explicit future live guard allows it.

Failure before HTTP must not mutate `providerPaymentKey`, must not emit `CaptureFacts`, and must not complete local order/payment.

## 7. Response normalization

D1 success requires:

```text
status === DONE
response.paymentKey === Payment.providerRef
response.orderId === deriveTossOrderId(Payment.id)
response.totalAmount === Payment.amount
response.currency === KRW, if currency is present
```

Normalize success as:

```text
providerPaymentKey = response.paymentKey
capturedAt = response.approvedAt, if valid
raw provider status = response.status
diagnostics = safe/redacted fields only
```

Rules:

- `DONE` is the only Toss status that can produce D1 local success.
- If `DONE` is returned but `approvedAt` is missing, use local `receivedAt` only as a fallback and include safe diagnostics.
- Do not persist raw Toss response in D1.
- Method-specific fields, receipt fields, and transaction fields are not persisted in D1.
- Any identity, status, amount, or currency mismatch must not emit `CaptureFacts`.

## 8. Amount/currency rules

- Toss D1 uses the local integer KRW amount directly.
- No decimal conversion is allowed.
- No rounding is allowed.
- Do not multiply KRW by 100.
- Pre-HTTP amount/currency mismatch is `STOP` or `PROGRAMMER_ERROR`.
- Post-response amount/currency mismatch is `MANUAL_REVIEW` and must not complete locally.
- Tests must enforce exact equality for local amount, request amount, and response `totalAmount`.

## 9. Idempotency mapping

Locked mapping:

```text
Idempotency-Key = Payment.providerConfirmIdempotencyKey
```

Rules:

- Local key `confirm:TOSS:{payment.id}` fits Toss's documented 300-character limit.
- Send the local canonical key directly unless a future official Toss constraint forces transformation.
- Never mint a new key after timeout, 5xx, provider unavailable, or `IDEMPOTENT_REQUEST_PROCESSING`.
- After Toss's idempotency retention window, do not blindly retry with a new key.
- If a future provider-specific transformation is lossy, that requires a new persistence decision before real adapter launch.
- Diagnostics may include a redacted, hashed, or truncated idempotency key. Diagnostics must not include secrets.

## 10. Error taxonomy

D1 Toss confirm states map to local categories as follows.

```text
IDEMPOTENT_SUCCESS
```

- Same idempotency key returns a successful Toss `Payment` object.
- The object must match `paymentKey`, `orderId`, amount, currency, and `DONE`.

```text
RETRYABLE
```

- Network timeout before response.
- HTTP 5xx/internal provider errors.
- `PROVIDER_ERROR`.
- `FAILED_PAYMENT_INTERNAL_SYSTEM_PROCESSING`.
- `FAILED_INTERNAL_SYSTEM_PROCESSING`.
- `IDEMPOTENT_REQUEST_PROCESSING`.

Retryable outcomes must reuse the same `Payment.providerConfirmIdempotencyKey`.

```text
TERMINAL
```

- User/payment method declines, including `REJECT_CARD_COMPANY`, `REJECT_CARD_PAYMENT`, and `REJECT_ACCOUNT_PAYMENT`.
- Expired or canceled payment session, including `NOT_FOUND_PAYMENT_SESSION`, unless local evidence makes provider state ambiguous.
- Toss `Payment` status `CANCELED`, `ABORTED`, or `EXPIRED` when returned by trusted lookup/confirm evidence.

Terminal outcomes do not complete locally. A new user payment attempt may be required.

```text
MANUAL_REVIEW
```

- `ALREADY_PROCESSED_PAYMENT` without a matching successful Toss `Payment` object.
- `UNKNOWN_PAYMENT_ERROR`.
- Any provider success-looking response with paymentKey, orderId, amount, currency, or status mismatch.
- Ambiguous timeout after idempotency retention has expired.
- Any state where provider may have captured funds but the adapter cannot prove the exact local identity and amount.

Manual-review outcomes must not emit `CaptureFacts`.

```text
STOP
```

- Auth or secret-key failures such as `INVALID_API_KEY`, `UNAUTHORIZED_KEY`, and `INCORRECT_BASIC_AUTH_FORMAT`.
- Unsupported mode, market, currency, or live guard failure.
- Provider contract mismatch that indicates unsafe adapter configuration.

STOP outcomes require operator/developer intervention before retry.

```text
PROGRAMMER_ERROR
```

- Malformed local request construction.
- Missing local `providerRef`.
- Invalid local idempotency key.
- Invalid derived local orderId.
- Invalid local amount shape before HTTP.

Programmer errors must fail before provider HTTP.

Official Toss docs do not distinguish every exact invalid case for bad `paymentKey`, bad `orderId`, and bad `amount`. D1 should treat `INVALID_REQUEST`, `FORBIDDEN_REQUEST`, and `NOT_FOUND_PAYMENT_SESSION` conservatively, and require sandbox/support confirmation before live launch.

## 11. Idempotent success / already confirmed policy

- Same idempotency key returning a matching successful Toss `Payment` object may be treated as idempotent success.
- Success requires matching `paymentKey`, `orderId`, amount, currency, and `DONE`.
- `ALREADY_PROCESSED_PAYMENT` alone is not enough for success.
- If no matching Toss `Payment` object or trusted lookup proves success, classify as `MANUAL_REVIEW`.
- Never retry with a new confirm key to "fix" already processed ambiguity.

## 12. Provider lookup / ambiguous state policy

- Ordinary timeout/retry inside Toss idempotency retention can retry the same key.
- If retention expired, do not mint a new key blindly.
- Ambiguous already-processed or unknown state requires either provider lookup or manual review.
- Provider lookup can be deferred from the fake mapper patch if ambiguous states return `MANUAL_REVIEW`.
- Before real money launch, implement lookup or write a manual-review runbook.

Official Toss lookup APIs relevant to a later design:

```text
GET /v1/payments/{paymentKey}
GET /v1/payments/orders/{orderId}
```

Those lookup APIs are not implemented by this design lock.

## 13. Security / redaction

Never log:

- `TOSS_SECRET_KEY`;
- Basic auth header;
- full `paymentKey`;
- raw Toss request/response;
- payer details;
- card details;
- receipt details.

Diagnostics are limited to:

- local payment id;
- provider;
- HTTP status;
- Toss code;
- safe class/message;
- derived orderId;
- masked paymentKey;
- idempotency hash/truncation.

Raw Toss bodies must not be persisted in D1.

## 14. Sandbox/live boundary

Future adapter factory requirements:

- Toss confirm adapter requires a server-side secret key.
- Test secret key begins with `test_sk`.
- Live secret key begins with `live_sk`.
- Mode comes from D1-A resolution.
- Live adapter creation requires explicit live allowlist.
- Normal `npm run verify` must use fake HTTP only.
- Unit/integration tests must make no real Toss calls.
- Real adapter creation must reject mismatched mode/key class before HTTP.

Current `resolveProvider` still returns mock-backed providers for every provider code. This document does not change that.

## 17. Stop conditions before real Toss confirm

Real Toss confirm remains blocked while any of these are true:

- sandbox/live guard is not implemented;
- real adapter is not wired;
- callback route is still non-completing;
- exact invalid input codes require sandbox/support confirmation;
- provider lookup/manual-review policy is not implemented;
- webhook verifier/parser is still mock-wired;
- real void taxonomy is unresolved;
- `VOID-HOOK-DEBT` is unresolved;
- no live enablement.
