# 결제 정책 결정 기록 (Payment Policy Decision Record) — v1

- **범위**: 글로벌 실물(주문제작 포함) 커머스의 결제 도메인 정책.
- **원천**: 지난 대화 「웹 커머스 결제 구조 설계」(A/C 비교~글로벌 PG 논의) + 이번 대화 4턴(확정 6개 정책 → 1차 보강 검토 → 외부 리뷰 평가 → P6 동시성 중재 심화).
- **지위 표기**:
  - `[확정]` 사용자가 확정한 정책 원문.
  - `[확정+보강]` 확정 정책에 이후 논의로 붙은 수정·구체화 — **보강 부분은 아직 권고 지위**이며 사용자 승인으로 확정됨.
  - `[채택 권고]` 신규 제안, 채택을 권함(미확정).
  - `[조건부 수용]` 외부 리뷰 제안을 조건을 달아 수용.
  - `[기록: 향후]` 지금은 구현하지 않되 자리(상태 필드·훅·기준)만 예약.
  - `[배제]` 검토 후 배제, 이유 명시.
  - `[확인 필요]` 시스템 외부(법률·PG 계약·DB 엔진·도메인 실측)에서 검증해야 확정 가능.

## 1. 최상위 불변식 `[채택 권고]`

개별 정책들의 상위에 두는 원칙. 아래 5개가 지켜지는 한 개별 메커니즘은 교체 가능하다.

1. **확정된 결제는 반드시 주문 생성 또는 환불(망취소) 중 정확히 하나로 귀결되며, 절대 무시되지 않는다.**
   - 근거: 외부 리뷰 제안을 상위 원칙으로 승격. §2.3의 (b)(c)(d)와 망취소 보상 큐를 하나로 묶는 문장이며, 대사 배치는 이 불변식의 검사기로 정의된다("결제 있음 + 주문 없음 + 취소 미완"이 위반 신호).
2. **결제 1건, 세션 1건당 주문은 최대 1개.** `(provider, paymentKey)` 유니크와 `orders.session_id` 유니크를 **둘 다** 건다(택일 아님 — 전자는 "같은 결제→두 주문"만, 후자는 "재시도로 결제키 2개→한 세션 두 주문"을 막음).
3. **금액의 진실은 서버 스냅샷.** confirm 시 PG 승인 금액 == 세션 스냅샷 금액을 서버에서 검증, 불일치는 망취소. 클라이언트가 보낸 금액은 절대 신뢰하지 않는다. (클라이언트 금액 조작은 커머스의 가장 흔한 공격 벡터인데 기존 (a)~(d)만으로는 안 잡힘.)
4. **confirm 경로는 살아있는 카트·현재 가격을 절대 재조회하지 않는다.** 카트→세션 동결은 결제 개시 시점에 동기적으로 끝난다. (결제 중 가격 변경 버그의 진원지 차단.)
5. **웹훅은 트리거일 뿐, 상태의 진실은 PG 조회 API.** 웹훅 수신 시 페이로드를 믿지 않고 조회 API로 재확인 — 순서 뒤바뀜·위변조 문제를 개별 대응이 아니라 구조로 소거. 비용은 조회 1회 추가뿐.

## 2. 확정 정책 6개 — 원문, 확정 근거, 보강

### 2.1 `[확정]` 주문 생성 시점 = 결제 성공 후 (Full C)

주문(Order)은 결제 성공 후 생성. 결제 전 캐리어로 CheckoutSession을 둔다. A′(경화판 A) 아님.

- **확정 근거**: ① A(체크아웃 시 PENDING Order)의 비용은 앞으로 만들 모든 쿼리·리포트·기능에 영구적·분산적으로 스며들지만, C의 비용(핸들러 견고화)은 일회성·국소적 — 시스템이 자랄수록 C가 유리. ② Order = 항상 진짜 주문이라는 타입 수준 보장으로 집계·다운스트림이 설계상 깨끗하고, 취소/환불 상태기계를 PENDING 오염 없이 설계 가능. ③ 설계안 단계라 마이그레이션 비용 0. ④ "돈 받고 주문 없음"이라는 C의 고전적 약점은 §2.3 보강으로 봉쇄되는 실패류이고, 국내 PG의 동기 confirm 흐름에서는 갭 자체가 크게 줄어듦.

### 2.2 `[확정+보강]` CheckoutSession = 백지 신규 정의

현 Order를 개명하지 않고 새로 정의. Order 설계는 입력으로만 취급.

- **보강(외부 리뷰 채택, 검증 결과 "강제된 수정"): 이행 *상태* vs 이행 *입력*의 구분.**
  - 이행 **상태**(운송장, 배송 진행, 제작 진행)는 세션에 없다 — 원칙 유지.
  - 이행 **입력**(배송지, 배송 방법, 수령인)은 세션 스냅샷에 **있어야 한다**. 근거 둘: ① 웹훅 경로는 브라우저 없이 주문을 만들어야 하므로 주문 생성의 전 입력이 세션에 있어야 성립. ② 글로벌에서는 배송지가 배송비·세금(EU VAT, 미국 주별 sales tax)을 결정하므로 **결제 금액이 배송지의 함수** — 배송지 없는 금액 스냅샷은 정의상 불완전.
  - 구현 제약: 주소는 **참조가 아니라 값 복사(또는 불변 버전 참조)**. 참조는 결제 개시~웹훅 사이에 수정·삭제될 수 있어 동결이 아님.
- 따라서 확정 정책 원문의 "배송/이행 필드는 결제 후 슬림 Order로"는 **"이행 상태는 Order로, 이행 입력은 세션 스냅샷으로"로 문구 수정**을 권고.

### 2.3 `[확정+보강]` §3 안전장치

#### (a) 결제 개시 시점 불변 스냅샷 — 명세 확장 `[채택 권고]`

스냅샷에 포함할 것과 각 항목의 존재 이유:

| 항목 | 이유 |
|---|---|
| 품목·수량·단가 | 기본. 결제 중 가격/구성 변경 차단 |
| **라인별 할인·쿠폰 배분액** | 부분환불 산식은 스냅샷 시점에 라인별 배분이 정해져야 정의됨. 총액만 얼리면 "라인 하나 환불 시 쿠폰 회수액"이 미정의 |
| **라인별 세액** | 부분환불·세무 처리의 전제 |
| 배송비(분해) | 일부 취소 시 배송비 환불 규칙의 기준 |
| 통화 + 적용 환율 | 표시통화 ≠ 정산통화일 때 금액 검증·환불의 기준 |
| **배송지·배송 방법·수령인** (값 복사) | §2.2 — 웹훅 경로 성립 + 금액의 입력 |
| 구매자 식별자 (게스트면 이메일) | 웹훅 경로에서 "주인 없는 주문" 방지 |
| **청약철회 배제 동의** (주문제작 상품) | 약관 고지만으로는 분쟁 증빙이 약함. 체크아웃 시점 동의를 스냅샷에 캡처해야 스냅샷=분쟁 증빙 원칙과 정합 `[확인 필요: 법률]` |
| 외부용 orderId | PG confirm 대조 + (동기 수단 한정) 고객 안내 아티팩트 |

#### (b) 멱등 주문 생성 — 구체화 `[채택 권고]`

- 유니크 제약은 `(provider, paymentKey)` **복합**으로 — 멀티 PG를 여는 순간 paymentKey는 PG 간 충돌 가능.
- `orders.session_id` 유니크를 **추가로** 건다 (§1 불변식 2의 근거).
- **중복 진입은 에러가 아니라 멱등 성공**: 기존 주문을 반환. 클라이언트 재시도가 사용자에게 실패로 보이면 안 됨 ("결제 성공했는데 에러 화면" 방지).
- 두 탭에서 별개 세션 2개가 각각 결제 성공하는 케이스: **시스템 예방이 아니라 사후 탐지**(동일 사용자·동일 구성·근접 시각 플래그 → CS/자동환불). 근거: 비용 대비 논거를 넘어, §3.1의 만료-레이스 규칙(만료가 완료를 못 막음) 하에서는 세션 만료로 이중 결제를 예방하는 것이 원리적으로 불가능 → 사후 탐지가 유일하게 정합적인 답(트레이드오프가 아니라 귀결).

#### (c) Payment 저장 + Order 생성 동일 트랜잭션 — 경계 명시 `[채택 권고]`

- **PG confirm 호출(외부 HTTP)은 반드시 DB 트랜잭션 밖.** 순서: confirm 호출 → 트랜잭션 시작(Payment, Order, 재고) → 커밋.
- 이로 인해 생기는 "PG 승인 성공 → DB 트랜잭션 실패" 창의 복구 경로를 명문화: 웹훅이 같은 멱등 경로로 재진입 → 그래도 놓치면 대사가 잡음 (§1 불변식 1의 실행 경로).
- **confirm 타임아웃 = 불확정 상태**: 실패로 추정 금지. PG 조회 API로 상태 확정 후 분기. 그 사이 사용자에게 보여줄 "결제 확인 중" 화면 필요 (§4.4).
- **부수효과(확인 메일, 물류 통지, 제작 트리거, 분석 이벤트)는 같은 트랜잭션에 넣지 않고 outbox 행으로 기록** → 별도 워커 발행. 메일 서버 장애가 결제를 실패시키는 결합 제거.

#### (d) 대사(reconciliation) 배치 — 방향·층위 확장 `[채택 권고]`

- **양방향**: ① 결제 있음·주문 없음 → (b)의 멱등 경로로 **자동 복구**. ② 주문 있음·결제 없음/취소됨 → **알람**(자동 삭제 금지). ③ 금액 불일치 → 알람.
- 점검 항목에 "결제 있음 + 주문 없음 + **취소 미완**" 추가 (망취소 실패 탐지, §2.5).
- 거래 대사와 별개로 **정산(수수료·입금액) 대사를 별도 층**으로 — 글로벌 PG는 수수료·환율 차감 구조가 달라 회계 불일치가 여기서 발생.
- 멀티 PG 시 PG별 분리 실행. 데이터 소스는 §4.5 이벤트 원장.
- 출시 첫날부터 가동 (초기 트래픽에서 결제 버그가 가장 많이 발생).

### 2.4 `[확정+보강]` ManufacturingRequest = dormant

주문 시 생성 → 결제 → PAID 후 제작. 제작 부작용은 PAID 이후.

- **보강 4개** `[채택 권고]`:
  1. **착수 시점 = 취소 정책의 분기점(point of no return).** PAID 후 제작 착수까지 유예창(무료 취소 가능)과 착수 후 취소 규칙을 정의하고, 착수 이벤트를 기록. §4.1 환불 상태기계와 연동.
  2. **청약철회 배제의 유효 요건.** 주문제작 상품 예외(KR 전자상거래법·EU 소비자권리지침의 맞춤제작 예외)는 체크아웃 시 명시 고지·동의가 있어야 유효한 것으로 파악 → 동의를 세션 스냅샷에 캡처(§2.3(a)). `[확인 필요: 법률 — 존재를 알린 것이지 요건 충족 판단이 아님]`
  3. **리스크 게이트.** 커스텀 제작품은 차지백 시 재판매 불가 = 전손 → 고위험 주문(고액·해외카드·배송지 불일치 등)은 PAID와 제작 착수 사이에 수동 검토 홀드 상태를 둠. §5.1과 연결.
  4. **트리거는 outbox 이벤트로.** PAID 트랜잭션 안에서 제작 시스템 직접 호출 금지 — §2.3(c)에서 뺀 결합을 다시 들이지 않기 위함.
- **SKU 유형 분기** `[확인 필요: 도메인]`: 주문제작 SKU는 차감 대상이 완제품 재고가 아니라 자재 또는 **생산 캐파(제작 슬롯)**일 수 있음. "조건부 차감"의 대상을 SKU 유형별로 정의하지 않으면 §2.5는 기성품에만 적용되는 반쪽 정책.

### 2.5 `[확정+보강]` 재고 차감 = 결제 완료 트랜잭션 내 원자 조건부 차감

`stock >= n` 조건부 차감, 실패 시 망취소. 세션 단계 예약은 스텁.

- **차감 순서 대안 검토**: (i) confirm 후 차감+망취소(현행) — **유지**. (ii) 차감 먼저 후 confirm — 외부 호출 동안 DB 락 보유이므로 `[배제]`. (iii) 예약 후 confirm 후 확정 — 스텁으로 이미 준비.
- **보강** `[채택 권고]`:
  1. **멀티 라인 all-or-nothing.** 한 라인만 차감 실패 시 전체 망취소. 부분 주문 생성은 스냅샷 금액과 어긋나 부분환불·재승인이 얽히므로 `[배제]`.
  2. **망취소 실패 대비.** 취소 API 호출 자체도 실패 가능 → 보상 재시도 큐 + 운영 알람 + 사용자 노출 상태("결제 확인 중, N분 내 자동 취소/환불" SLA). 돈이 빠졌는데 주문이 없는 상태를 사용자가 보는 유일한 창.
  3. **예약 레이어 활성 기준을 지금 지표로 정의.** 예: "결제 후 품절 망취소율 > 임계치". "필요할 때 켠다"는 판단 주체와 신호가 없으면 켜지지 않음.
- **결정 만료일**: "즉시 완료 수단은 품절 창이 초 단위"라는 현행안의 근거는 카드+월렛 커버리지 전제에 묶임. **지연완료 수단(가상계좌류, 편의점, Boleto 등)을 여는 순간 재방문** — 글로벌 확장과 동시에 도래하므로 생각보다 가까움 (§7).

### 2.6 `[확정+보강]` 완료 로직 = 공유 단일 트랜잭션 (confirm 동기 + 웹훅 백업)

완전 비동기화(주문 생성까지 큐로) 배제 유지.

#### (i) 동시 진입 중재 = 하이브리드 `[채택 권고]`

**세션 행 잠금(`SELECT … FOR UPDATE`)을 트랜잭션 첫 줄에 두어 중재하고, 유니크 제약(§2.3(b))은 폐기하지 않고 최후 방어선으로 유지.**

- **전제 교정 2개**(이 결정의 논거 구조):
  - "한 메커니즘이 중재+유일성을 겸해야 한다"는 전제 해체 — 중재(누가 수행하나: 성능·코드 경로)와 유일성(어떤 경로로도 주문 2개 불가: 정확성 불변식)은 다른 문제. 유니크 제약은 §2.3(b) 그 자체라 제거 대상이 아니므로 실제 선택지는 "제약만으로 중재까지 시키느냐, 중재용 잠금을 앞에 더 두느냐".
  - "유니크 제약 = 낙관 = 비차단"이라는 전제는 이 사례에서 불성립 — MVCC 계열 DB에서 두 번째 트랜잭션은 유니크 인덱스·세션 행·재고 행에서 어차피 대기함. 차이는 블로킹 위치가 명시적 한 지점이냐 흩어져 있느냐뿐. 남는 비교축은 패자 경로의 가독성과 실패 지점의 예측 가능성.
- **잠금 채택 근거 3개**: ① §2.3(c) 결정(PG 호출은 트랜잭션 밖) 덕에 잠금 보유 시간이 DB 쓰기 몇 건 = ms 단위 — 이전 결정이 이 결정의 비용을 이미 지불. ② 데드락 위상이 깨끗함: 같은 세션의 confirm/웹훅은 같은 행을 원하므로 순수 대기열(사이클 불가), 다른 세션끼리는 세션 행이 겹치지 않음. ③ 패자가 부수효과 코드를 아예 실행하지 않는 유일한 방식 — 모든 진입점(confirm·웹훅·대사 복구)이 문자 그대로 같은 핸들러를 탄다는 P6 취지와 정합.
- **유니크 제약 단독 중재 `[배제]`**: 블로킹 이점이 허상이고, 패자 경로가 예외 기반 제어흐름이 됨(어느 제약이 먼저 터질지 INSERT 순서 의존, 위반 시 트랜잭션 전체 중단 → 롤백·재조회·성공 매핑을 예외별 구현). 결정적으로 §2.5(트랜잭션 내 재고 차감) 때문에 패자가 제약 위반 전에 재고 행 경합까지 일으키고 전부 롤백으로 버림.
- **기타 배제**: 어드바이저리 락(스키마에 안 보여 새 코드 경로가 빠뜨리기 쉬움; 행 잠금이 MVCC에서 일반 읽기를 안 막으므로 이점 무의미), Redis 분산 락(DB 커밋과 원자적으로 안 묶이는 두 번째 인프라 — 만료 시간 vs 트랜잭션 길이 문제), 큐 직렬화(= 이미 배제한 완전 비동기화의 재도입).
- **함께 확정할 운영 규칙**:
  - 잠금 순서: **세션 행 → 재고 행(들), 재고 행은 상품 ID 정렬 순** — 다른 세션들이 같은 SKU 조합을 다른 순서로 잠그며 생기는 데드락(§2.5에 내재)을 정렬로 차단.
  - 잠금 획득 후 첫 동작 = 상태 재검사: COMPLETED → 기존 주문 멱등 반환, EXPIRED → §3.1 honor window 분기.
  - **잠금이 있는데 유니크 위반 발생 = 정상 경합이 아니라 "잠금을 안 탄 경로 존재"라는 버그 신호** → 사용자에겐 멱등 성공, 내부 알람.
  - 웹훅 쪽 `NOWAIT` + 비-2xx 응답(PG 재전송에 위임)은 부하가 문제 될 때 붙이는 국소 최적화로 보류.
- **결정 만료 조건 2개** (§7): 예약 레이어 활성으로 재고 차감이 트랜잭션 밖으로 나가면 제약 단독 중재의 감점이 사라져 재비교 가치 발생. 주문/결제 서비스·DB 분리 시 행 잠금 자체가 불성립 → outbox/saga로.

#### (ii) 웹훅 취급 `[채택 권고]`

서명 검증, PG 원본 페이로드 append-only 보존(§4.5), **트리거로만 사용 + 조회 API로 상태 재확인**(§1 불변식 5).

#### (iii) 역할의 일반화 `[채택 권고]`

"confirm 주 경로, 웹훅 백업"은 국내 PG의 카드형 동기 승인 흐름에 묶인 결론. 글로벌의 리다이렉트(3DS)·지연완료 수단에서는 **웹훅이 주 경로**가 됨. P6을 폐기하지 않되, **수단별로 주/백업 역할이 뒤집힐 수 있는 구조**로 핸들러를 설계.

## 3. 조건부 수용 항목 (외부 리뷰 평가 결과)

### 3.1 세션 만료 vs 늦은 승인 레이스 `[조건부 수용]`

- **수용한 것**: "만료는 새 결제 *개시*만 막고, PSP 확정 신호는 만료 여부와 무관하게 공유 핸들러로 흘려 완료를 시도한다." 이는 지난 대화의 결론("만료 후 승인 = 자동 망취소")을 **명시적으로 대체**함 — 두 기록이 반대라는 점을 리뷰가 고지하지 않아 여기서 명문화.
- **수용 근거**: 동기 수단에서 만료~늦은 승인 갭은 보통 분 단위 → 동결 스냅샷을 존중해 완료하는 것이 전환율·CS 비용에서 유리. 재고는 어차피 같은 조건부 차감을 통과하므로 오버셀 없음. 커스텀 제작품은 플래시세일형 가격 변동 상품이 아니라 스냅샷 가격 존중의 사업 리스크가 작음.
- **조건 3개** (없으면 수용 철회):
  1. **외곽 시한(honor window)**: 동결 후 X시간 내 도착분만 완료, 초과분은 망취소. 무제한 honor는 프로모션 종료·가격 개편과 충돌 → `[배제]`.
  2. 상태기계에 **EXPIRED → COMPLETED 전이를 명시적으로 허용** (안 하면 구현이 전이를 막아 불변식 1 위반 발생).
  3. **세션 아카이브 지연 > honor window** — 안 지키면 "완료 가능한 세션이 이미 삭제됨"이라는 자기모순. (리뷰의 두 권고가 서로를 참조하지 않아 생긴 틈을 여기서 봉합.)

### 3.2 비동기(지연완료) 결제 수단 대응 `[조건부 수용]`

- **지금 채택**: 선택지 (i) — **동기 수단(카드·월렛)만 지원함을 설계 경계로 명시적 선언·문서화.** 현행 정책 1~6 유지 가능.
- **유보한 것**: 리뷰의 "(ii) AWAITING_PAYMENT 주문이 사실상 표준이므로 미래 기본 후보" — **기본값으로 예약하지 않음.**
  - 근거: "(iii) 세션 수명 연장 + 예약 = 이름만 다른 (ii)"라는 리뷰 논증은 C를 택한 원래 이유를 과소평가. 두 안의 실질 차이는 대기 레코드가 사는 테이블과 고객 안내 아티팩트뿐이고, **재고 예약은 (ii)에서도 똑같이 필요**(입금 대기 중 재고를 안 잡으면 동일한 오버셀). 반면 가상계좌류는 미입금 이탈률이 높은 수단이라 (ii)를 택하면 대량의 버려진 대기 레코드가 — C로 막 정화한 — Order 공간을 다시 오염. 즉 (iii)은 "오염이 무해한 테이블에 대기를 두는 안"으로서 독립적 가치가 있음.
  - **그 시점의 결정 기준 2개만 기록**: ① 다운스트림(ERP·CS 관행·오픈마켓 연동)이 '입금대기 주문'이라는 개체를 요구하는가 → 요구하면 (ii)가 이김. ② 세션의 외부용 orderId가 고객 안내 아티팩트로 충분한가 → 충분하면 (iii) 유리. `[확인 필요: 도메인 — 대상 시장별 미입금율 실측이 판단 변수]`

### 3.3 두 탭 이중 결제 → §2.3(b)에 통합 기록 (사후 탐지, 귀결로서 채택).

## 4. 신규 정책 — 런칭 블로킹 `[채택 권고]`

### 4.1 취소·환불 상태기계 (최대 공백)

현재 확정 6개는 전부 돈이 들어오는 절반. 나가는 절반이 상용화의 실제 병목(취소는 전액/부분/배송 후 반품/망취소가 각각 다른 경로 + 청약철회권 때문에 선택이 아니라 필수).

- Cancellation 엔티티: 전액/부분(라인 단위 — §2.3(a)의 라인별 배분 스냅샷이 전제), 환불 금액·사유.
- 환불 요청의 멱등키 (결제와 동일한 원칙을 역방향에도).
- 주문 상태기계 `PAID → IN_PRODUCTION → SHIPPED → DELIVERED`와 상태별 취소 가능 여부. 커스텀 상품의 제작 착수 컷오프는 §2.4-1과 연동.
- 배송비 환불 규칙(전체 취소 vs 일부 취소), 쿠폰·적립금 역배분 규칙, PG 정산 전/후 환불 경로 차이, 환불 시 재고/제작 슬롯 복원 규칙.
- 청약철회 예외의 고지 요건은 약관 명시 필요 `[확인 필요: 법률]`.

### 4.2 금액 표현 정책 (스키마상 가장 되돌리기 비쌈)

정수 최소단위 저장(부동소수점 금지), 통화별 라운딩(JPY 소수 0자리 등), 표시통화·청구통화·정산통화의 구분, 환율 적용·고정 시점(스냅샷). 전부 §2.3(a) 명세로 귀결.

### 4.3 세금·관세 정책 — **순서 의존 주의**

지역별 가격 표시(세금 포함/별도 — EU는 포함가 표시 의무), 세액의 스냅샷 포함, 국경 간 실물 배송의 관세 부담 주체(DDP/DDU). **이 정책은 계약 주체/MoR 결정에 종속** — 지난 대화에서 진행 중이던 그 결정이 미확정 상태이므로 선행되어야 함 (§8).

### 4.4 결제 실패·재시도 UX 정책

실패 후 같은 세션 재사용 vs 새 세션 발급, 사용자당 활성 세션 정책(이중 탭), 완료 페이지 새로고침·뒤로가기 멱등. **예외 경로 전용 "결제 확인 중" 상태·화면**(confirm 타임아웃 시) — 완전 비동기화 배제 결정과 모순 아님: 기본 흐름이 아니라 fallback.

### 4.5 결제 이벤트 원장

주문·결제 레코드와 별개로 PSP와 주고받은 **모든** 이벤트를 append-only 기록(원본 페이로드 포함). 대사(§2.3(d))의 데이터 소스이자 분쟁(§5.1) 증빙.

### 4.6 CS·감사·보존 정책

- Order 없는 실패/취소 결제를 세션·Payment 키로 조회하는 CS 경로 (실패 결제엔 주문번호가 없음).
- 세션 정리는 **물리 삭제가 아니라 만료 → 일정 기간 아카이브 → 삭제로 단계화** (퍼널 분석·대사 소급 조회 보존). 아카이브 지연 > honor window (§3.1-3).
- 보존 기간: 전자상거래법 거래기록 보존 의무의 범위, 특히 **실패한 결제 시도가 포함되는지** `[확인 필요: 법률]`.

## 5. 신규 정책 — 출시 후 `[기록: 향후]` (지금은 상태 필드·훅·기준만 예약)

### 5.1 차지백·분쟁 대응
Dispute 상태, 분쟁 접수 시 이행 중단 훅(특히 제작·출고), 증빙 패키지(세션 스냅샷·커스터마이징 확인 기록·배송 추적 — §2.3(a)·§4.5가 원천). 초기엔 수동 대응으로 충분하되 상태 모델에 자리 확보. **승격 조건**: 주문제작 비중이 높으면 §2.4-3 리스크 게이트와 함께 런칭 블로킹으로 재분류 검토 (커스텀 상품은 차지백 시 재판매 회수 불가 = 일반 커머스보다 타격 큼).

### 5.2 부정거래 방어
세션 생성 속도 제한(카드 테스팅 공격은 **결제 실패 트래픽**으로 옴 — 성공 경로 모니터링만으론 못 봄), 벨로시티 룰, 3DS 적용 기준.

### 5.3 혼합 결제 (적립금/쿠폰 + 카드)
소비 시점(개시 시 예약 vs 완료 시 소비), 동시 세션 이중 사용 방지, 환불 시 역순 환원. §2.3(a)가 라인별 배분을 이미 담으면 증축 용이.

### 5.4 auth/capture 분리
지금은 `[배제]`(즉시 매입이 초기 운영 단순). 단 Payment 상태 모델에 AUTHORIZED↔CAPTURED를 나중에 끼울 여지를 남길지는 **지금 결정할 문제** — 글로벌 실물엔 배송 시 매입 관행 시장이 존재.

### 5.5 다중 PG 라우팅 자동화 — 멀티 PG 계약이 실재해진 뒤.

### 5.6 세션 단계 재고 예약 레이어 — §2.5-3의 활성 지표 충족 시 또는 지연완료 수단 도입 시.

| 무제한 honor window | 프로모션 종료·가격 개편과 충돌 |
| 늦은 승인 무시 | 돈은 나갔는데 주문도 환불도 없음 — 불변식 1 위반, 최악의 사고 유형 |

## 8. 확인 필요 플래그 (외부 검증 없이는 확정 불가)

- **법률**: 청약철회 배제의 고지·동의 요건(KR 전자상거래법, EU 소비자권리지침), 거래기록 보존 범위(실패 시도 포함 여부), 통신판매업 신고·구매안전서비스(에스크로) 적용 — 본 문서는 존재를 알린 것이지 충족 판단이 아님.
- **PG 계약**: confirm 중복 호출 시 응답 동작, 웹훅 재전송·서명 방식, 망취소 가능 시한 — 계약할 PG의 최신 연동 문서로 확정.
- **DB 엔진**: 유니크 인덱스 대기/위반 의미론, InnoDB 중복 키 공유 잠금 데드락 패턴 — §2.6(i)은 Postgres/InnoDB급 의미론 전제로 검증했고 실제 채택 엔진은 미확인.
- **도메인 실측**: 제작 슬롯 구조·리드타임(§2.4 컷오프 설계 변수), 대상 시장별 미입금율(§3.2 판단 변수).
- **미결 상류 결정**: 계약 주체/MoR (지난 대화의 마지막 미완 주제) — §4.2·§4.3과 §2.3(b) 복합 유니크의 구체화가 걸려 있음.

## 9. 실행 순서 권고

1. **세션 스냅샷 명세 확정** (§2.3(a) — 배송지·라인별 배분·통화·동의 포함 여부까지). 웹훅 경로의 성립 조건이자 금액 검증·분쟁 증빙·환불 계산의 기준점이 전부 여기 걸림.
2. **취소·환불 상태기계** (§4.1). 1과 상류/하류 관계 — 스냅샷이 흔들리면 환불 산식이 같이 흔들림.
3. 두 가지 모두 **스키마 동결 전에.** 병행: MoR/계약 주체 결정(§8) → §4.2·§4.3 착수.

## 10. 이 문서의 검토 경계

- 다루지 않은 축: 정기결제/빌링키, 마켓플레이스형 정산 분배·에스크로, B2B 후불/세금계산서, 암호화폐, 오프라인 결제, 쿠폰·프로모션 엔진 자체의 설계(스냅샷 접점만), 성능/스케일링, PCI-DSS 상세(카드 정보가 서버에 닿지 않는 호스티드 방식 전제 — 아니라면 별도 검토), 제작 이후의 생산·물류 워크플로(결제와의 접점만).
- 전제: 단일 DB, 단일 창고, 출시 규모 트래픽.
- 본 문서는 대화 기록만으로 작성되었고 실제 스키마·코드는 열람하지 못함. 외부 리뷰와 본 검토가 다수 항목에서 독립 수렴했으나, **수렴이 법률·PG·DB의 외부 확인을 대체하지 않음** (§8).
