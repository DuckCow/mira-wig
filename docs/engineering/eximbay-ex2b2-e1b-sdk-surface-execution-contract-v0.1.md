## 1. Goal and frozen boundary

After reviewed installation and a separate explicit invocation, authorize one
bounded E1B execution that answers only:

> Can the **current installed Mira `loadEximbaySdkV2("SANDBOX")` loader**, in a
> fresh disposable real Chromium document, load the current canonical Eximbay
> TEST v2 SDK and resolve to a callable captured `request_pay` function without
> invoking it?

```text
E1B:
  non-completing real SDK load / global / browser-surface evidence only

E1B IS NOT:
  request_pay once
  payment page opens
  payment-producing browser exercise
```

`EXIMBAY.request_pay` invocation and any payment-page popup or redirect are
outside E1B. End-to-end payment-producing browser evidence remains separately
gated after BF4 under E2 or later authority.

Only documentation pages were read while preparing this candidate. No Eximbay
API origin or SDK asset was contacted.

This contract is subordinate to the
[EX2B2 Design Contract v0.2](./eximbay-ex2b2-ready-transport-sdk-handoff-design-contract-v0.2.md).
It does not define branch semantics and cannot broaden, amend, or supersede the
governing design.

```text
GOVERNING DESIGN:
  EX2B2 READY Transport + JavaScript SDK Browser Handoff Design Contract v0.2
  after its human-reviewed installation

THIS CONTRACT:
  binds one separately human-authorized E1B execution only
  cannot broaden or supersede the governing design
```

Design Contract v0.2 owns the prospective E1A/E1B independent-branch
semantics. Under that design, account-bound E1A remains
`DEFERRED / NOT SATISFIED`; E1B consumes no E1A or MIRA-PUBLIC-READY-1
evidence, READY authority, FGKey, merchant credential, Payment state, or
merchant capability. MIRA-PUBLIC-READY-1 remains separate admitted evidence,
not an E1B prerequisite.

Before both Design Contract v0.2 and this execution contract are
human-reviewed and installed, E1B execution is `NOT AUTHORIZED`. Their
installation can make only one separately human-authorized E1B invocation the
next gate. This contract grants no standing or repeatable SDK-load authority.

## 5. Guarantees

One separately authorized E1B invocation freezes all of these guarantees:

1. the exact current source baseline is checked before execution;
2. only `SANDBOX` mode is allowed;
3. the browser uses a fresh disposable profile/document with no signed-in
   Mira or customer state;
4. the harness imports and executes the current production `sdk-loader.ts`
   bytes, not a reimplementation;
5. at most one E1B-controlled SDK script insertion/load attempt is allowed;
6. automatic retry is zero;
7. if SDK load may have occurred, the one invocation authority is consumed;
8. PASS requires the loader's returned captured value to be callable;
9. `request_pay` invocation is zero;
10. READY/API contact is zero;
11. API key, MID, Authorization, and FGKey use is none;
12. Payment database/state use is zero;
13. payment page, card/payment information, BF4, and completion are zero;
14. source, schema, config, dependency, CSP, routing, and checkout changes are
    prohibited;
15. customer, production, and existing browser-profile data are prohibited;
    and
16. one small sanitized external result is sufficient; no custody framework is
    created.

The invocation must not contact LIVE, call READY merely to obtain an FGKey,
create a production application consumer, enable Eximbay routing or checkout,
or use the existing `sdk-invocation.ts` request-pay controller.

## 6. Non-goals

E1B does not test or establish:

- payment-page popup or redirect behavior;
- user-gesture behavior;
- `request_pay` semantics;
- FGKey matching;
- return/status callback behavior;
- card or payment-method capability;
- financial correctness;
- merchant-account capability;
- headed-browser UX;
- production checkout integration;
- LIVE SDK reachability;
- BF4 verification or completion readiness; or
- E2/payment-producing browser authority.

Successful E1B evidence cannot be used to infer merchant/account capability,
payment readiness, or production readiness.

## 7. Minimal temporary browser harness

The harness must exist outside the repository working tree and add no
dependency. The bounded preferred implementation, when already available on
the operator machine, is:

- an existing Google Chrome or Chromium executable;
- a fresh temporary browser user-data directory;
- the repository's already-installed `esbuild` to bundle a tiny browser entry
  that imports the real current `sdk-loader.ts`;
- an already-installed system or Node tool serving only on loopback;
- a headless real Chromium document; and
- a local DOM marker as the only browser-facing PASS/FAIL output.

The browser entry calls only:

```ts
const captured = await loadEximbaySdkV2("SANDBOX");
```

It may observe the loader-owned script insertion to count the controlled
attempt and compare the element's resolved `src` with the exact canonical TEST
v2 source. It must only test `typeof captured === "function"`. It must never
call `captured`, `EXIMBAY.request_pay`, the production invocation controller,
READY, or any other provider API.

If the existing browser, bundler, or loopback serving tool is unavailable, the
execution stops precontact. Do not install Playwright, Puppeteer, Selenium, or
another dependency for E1B. Headless evidence is not headed payment-page or UX
evidence.

The temporary page, bundle, server state, and disposable profile must be
removed after the result is written. A cleanup failure is reported in the
sanitized result and is not repaired by an SDK retry.

## 8. Contact ceiling, safe STOP, and re-entry

```text
controlled SDK script insertion/load attempts:
  at most 1

automatic retry:
  0

request_pay:
  0

READY/API:
  0

LIVE:
  0
```

Tool and baseline checks happen before browser launch. Once the controlled SDK
script may have been appended or requested, the E1B authority is consumed
regardless of success, timeout, browser failure, or ambiguous load. There is no
same-authority rerun, fallback v1 SDK, or LIVE fallback. Any later attempt
requires new human adjudication and authority.

## 9. Sanitized result

Write one JSON result outside the repository. It contains only:

- schema name and version;
- execution source `HEAD` and tree;
- SHA-256 of current `sdk-loader.ts` and temporary harness bytes;
- browser product and version;
- environment class `PUBLIC_TEST_SDK_SURFACE`;
- expected SDK source classification;
- loader outcome;
- exact-script-source matched boolean;
- callable-captured boolean;
- controlled script insertion attempts;
- retry count;
- `requestPayInvoked: false`;
- READY/API, credential, BF4, and payment counts, all zero; and
- disposable browser-profile cleanup result.

Do not persist the SDK JavaScript response body, cookies or profile data,
credentials, an FGKey, or a raw general browser log/network dump. A later
bounded human diagnosis may separately authorize the minimum failure detail it
needs.

## 10. PASS and failure disposition

PASS requires all of:

```text
real TEST v2 SDK load attempt: 1
loader resolved: true
exact expected SDK source: true
captured request_pay callable: true
request_pay invocation: 0
READY/API credential use: 0
payment/BF4: 0
retry: 0
```

A successful script load without a callable captured by the current Mira
loader is not PASS.

On timeout, script error, missing callable, loader block, browser/tool mismatch,
or ambiguous external load: do not retry, do not call `request_pay`, do not
fall back to v1 or LIVE, and STOP with only sanitized failure facts.
